API Gateway Routing

Act 01

The Problem

Không có gateway, web và mobile phải biết địa chỉ của từng service và gọi thẳng. Richardson chỉ ra năm hệ quả: nhiều endpoint, giao thức khác nhau, cross-cutting concerns phân tán, bề mặt tấn công rộng, và API nội bộ không hợp với client (§8.1).

Coupling

Client gắn chặt với sơ đồ nội bộ

Frontend giữ URL của mọi service; tách, gộp hay đổi chỗ một service là phải sửa client. API nội bộ thiết kế cho máy chủ gọi máy chủ, trả dư dữ liệu hoặc bắt client gọi nhiều vòng — nặng nhất với mobile.

Phân tán

Mỗi service tự làm xác thực, CORS, rate limit

Mỗi nơi một bộ phân tích JWT, một cấu hình CORS, một cách giới hạn lưu lượng: mã trùng lặp và chính sách trôi dạt. Mọi endpoint nội bộ lộ ra Internet làm bề mặt tấn công rộng thêm.

2
Act 02

The Pattern

Mọi request của client đi qua một điểm vào duy nhất. Gateway xử lý tập trung các việc cắt ngang ở biên — CORS, xác thực, rate limit, logging — rồi định tuyến tới đúng service. Gateway không chứa business logic.

— Chris Richardson · Microservices Patterns, Ch.8

Đánh đổi: được một chỗ quản lý chính sách và che sơ đồ nội bộ; mất ở chỗ gateway thành điểm lỗi duy nhất (phải chạy nhiều instance sau load balancer) và dễ bị nhồi logic nghiệp vụ thành một monolith mới. Gateway kiểm tra ở biên, nhưng service đích vẫn xác minh bằng chứng danh tính và tự authorize (§8.1, §8.4).

Thành phần 01

Route + Predicate

Route nối một điều kiện với URI đích; Predicate là phép thử Path, Method… Ví dụ KBM: Path=/api/core/** → lb://kbm-core.

Thành phần 02

Filter chain

Filter chạy trước/sau bước định tuyến: gỡ header định danh do client tự gửi, kiểm tra JWT (alg, chữ ký, iss, aud, exp, nbf), rate limit, gắn correlation ID.

Thành phần 03

lb:// + StripPrefix

lb:// tra Eureka, chọn instance (round-robin) và chuyển tiếp. StripPrefix=2 đổi /api/core/questions thành /questions — service không cần biết mình được gắn ở đâu trên gateway.

Act 04 — Case Study

KBM: Apply It

KBM có hai loại gateway: Spring Cloud Gateway cho LMS core (route theo path, JWT, CORS, rate limit) và một router theo hostname viết bằng Go cho DevOps Lab (định tuyến workspace, gắn với k3s/Sysbox). Một gateway chung là đủ cho LMS vì các web frontend cần API tương tự nhau; BFF chỉ đáng thêm khi có mobile app hay client có nhu cầu API khác hẳn (§8.1, §8.5).

Gap Analysis — cấu hình Gateway

Trích bảng phân tích cấu hình Gateway của KBM (§8.5)
Khía cạnh Hiện trạng KBM Mức độ Hướng xử lý
CORS allowedOrigins: "*". HIGH Liệt kê origin cụ thể của các frontend; khai báo allowed-headers (thiếu là preflight kèm Authorization bị từ chối).
Identity validation Gateway kiểm tra JWT; downstream lẫn giữa tin header và tự parse token, với JJWT 0.11.5 ở Gateway và 0.9.1 ở service. HIGH Đồng bộ thư viện và hợp đồng xác minh; Spring Security OAuth2 Resource Server; RS256/JWKS; token exchange thay cho plain header.
Correlation ID Không có. MED GlobalFilter gắn X-Correlation-Id (UUID) cho mọi request.
Rate limiting Đã có Redis token bucket. LOW Tinh chỉnh cho chế độ thi: giới hạn riêng cho /submissions/**.

Lộ trình chuyển đổi

Theo đề xuất migration ở §8.5 — chưa phải việc KBM đã làm
Giai đoạn 1 · Tăng cường bảo mật

CORS allowlist, gỡ X-User-*, thống nhất hợp đồng JWT

Liệt kê origin cụ thể; gỡ mọi X-User-* từ client, giữ Authorization cho tới khi có token nội bộ có chữ ký; thống nhất thư viện và kiểm tra alg/iss/aud/exp/nbf; chứng minh bằng cấu hình rằng chỉ Gateway gọi được service nội bộ.

Ưu tiên cao · chi phí thấp
Giai đoạn 2 · Observability

Correlation ID và request logging

GlobalFilter gắn X-Correlation-Id; ghi log request/response tại Gateway để truy vết xuyên service.

Ưu tiên trung bình
Giai đoạn 3 · Bảo vệ và phân tầng tin cậy

Rate limit cho contest, giới hạn payload, RS256/JWKS

Giới hạn riêng cho /submissions/**, giới hạn kích thước tệp tải lên; chuyển sang RS256/JWKS và signed identity propagation đúng audience; workload identity/mTLS cho luồng nhạy cảm.

Ưu tiên trung bình

Khi nào dùng — Khi nào không

✓
Một API Gateway chung đủ khi
  • Các client (web sinh viên, web quản trị) cần dữ liệu tương tự nhau.
  • Muốn một chỗ duy nhất cho CORS, xác thực ở biên, rate limit, correlation ID.
  • Đội nhỏ, chưa có mobile hay đối tác bên ngoài với nhu cầu API riêng.
✗
Cân nhắc thêm / tránh khi
  • Có mobile app cần batched API và payload gọn → thêm Mobile BFF do đội mobile sở hữu.
  • Muốn gateway điều phối nghiệp vụ (tạo bài nộp rồi cập nhật điểm) — đó là việc của domain service/Saga.
  • Chỉ chạy một instance gateway — nó thành điểm lỗi duy nhất của cả hệ thống.
  • Coi request đi qua mạng nội bộ là đã xác thực — service đích vẫn phải xác minh bằng chứng.
