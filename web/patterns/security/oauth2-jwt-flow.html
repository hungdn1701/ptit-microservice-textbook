1
Act 01

Nghẽn cổ chai Xác thực & Rò rỉ khóa bí mật

Trong kiến trúc Microservices, nếu mỗi request của Client đi vào hệ thống đều bắt các service con gọi đồng bộ ngược lại Auth DB để kiểm tra Session, hệ thống sẽ gặp hiện tượng thắt cổ chai và mất khả năng chịu lỗi. Hơn nữa, việc sử dụng các thuật toán ký đối xứng (Symmetric Key) mang lại rủi ro an ninh nghiêm trọng.

💥

Thắt cổ chai cơ sở dữ liệu Auth (Auth DB Bottleneck)

Khi hàng ngàn request đồng thời đổ vào hệ thống, việc gọi vào Auth DB để validate Session cho từng request làm DB quá tải. Nếu Auth Service bị sập, toàn bộ các dịch vụ khác (dù không yêu cầu đăng nhập) cũng bị treo cứng theo.

🔑

Rủi ro từ Khóa đối xứng (Symmetric Key Leak)

Với thuật toán HS256, cả dịch vụ cấp token (Auth Service) và dịch vụ verify token (Resource API) đều dùng chung một Secret Key. Nếu một microservice bất kỳ của bên thứ 3 hoặc máy trạm chấm bài bị xâm nhập và lộ khóa bí mật, hacker có thể tự sinh token giả mạo quyền ADMIN.

2
Act 02

Chữ ký số bất đối xứng & Cặp đôi Tokens

Sử dụng cơ chế mã hóa bất đối xứng **RS256**: Auth Service giữ **Private Key** bảo mật tuyệt đối để ký Token. Các service con chỉ cần có **Public Key** (có thể công khai rộng rãi) để xác thực chữ ký. Để tăng an toàn, hệ thống cấp cặp token: **Access Token** (thời hạn ngắn, ví dụ: 15 phút) để gọi API và **Refresh Token** (thời hạn dài, ví dụ: 7 ngày) được lưu trữ an toàn để đổi lấy Access Token mới mà không cần bắt user đăng nhập lại.

— Token-based Authentication · OAuth 2.0 & RFC 7519 (JWT)

Cơ chế xác thực token phi tập trung (Decentralized Authentication) thông qua chữ ký số giúp hệ thống hoàn toàn stateless: các dịch vụ không cần gọi lại DB xác thực, chỉ cần kiểm tra toán học trên chữ ký của JWT.

Thành phần 01

Authorization Server

Nơi duy nhất xác thực credentials (user/password) và ký phát hành cặp Access/Refresh Token bằng Private Key. Định kỳ xoay vòng khóa (Key Rotation) để nâng cao bảo mật.

Thành phần 02

Resource Server

API Gateway hoặc các microservices nội bộ. Chúng tải Public Key từ Auth Service về cache. Khi nhận request, chúng tự giải mã chữ ký JWT mà không cần gọi mạng (Zero-network Validation).

Thành phần 03

Refresh Token Flow

Khi Access Token hết hạn, Client App gửi Refresh Token lên Auth Service. Auth Service kiểm tra tính hợp lệ trong database, nếu OK sẽ cấp một Access Token mới mà người dùng không hề hay biết.

Các bước di chuyển luồng Auth sang RS256
Phase 1 · Tuần 1

Tạo cặp khóa RSA Private/Public

Sử dụng OpenSSL sinh cặp khóa RSA 2048-bit. Cấu hình kblab-auth tải Private Key từ Secret Manager (Vault/KMS). Expose Public Key qua JWKS endpoint (/.well-known/jwks.json).

Dự kiến: 1 dev × 2 ngày
Phase 2 · Tuần 2

Cấu hình Gateway Resource Server

Cấu hình Spring Security OAuth2 tại kblab-gateway tự động fetch Public Key từ JWKS. Thực hiện validate token cục bộ phi tập trung tại Gateway.

✓ Đảm bảo Gateway chặn đứng token giả
Phase 3 · Tuần 3

Tích hợp Refresh Token Flow phía Frontend

Cấu hình interceptor tại Axios/Fetch trên App Client. Khi gọi API nhận lỗi 401, tự động gọi API /oauth2/token sử dụng Refresh Token lưu trong HttpOnly Cookie để lấy token mới.

Dự kiến: 1 dev × 4 ngày
Phase 4 · Tuần 4

Xây dựng Redis Token Blacklist chống thu hồi

Mặc dù JWT stateless không thể thu hồi, KBLab triển khai blacklist trên Redis. Khi user Logout hoặc Đổi mật khẩu, Access Token ID được đưa vào blacklist Redis trong thời gian sống còn lại (15 phút) để từ chối ngay lập tức.

✓ Khả năng thu hồi token tức thời

Khi nào dùng — Khi nào không

✅
Nên dùng RS256 & OAuth2 khi
  • Kiến trúc gồm nhiều microservices phát triển bởi nhiều team khác nhau
  • Hệ thống yêu cầu độ bảo mật cao, cần ngăn ngừa rò rỉ khóa bí mật
  • Cần hỗ trợ tích hợp đăng nhập từ bên thứ ba (Single Sign-On - SSO)
  • Số lượng request đọc thông tin cá nhân lớn, cần validate stateless phi tập trung
❌
Không nên dùng khi
  • Ứng dụng monolith nhỏ, phân quyền đơn giản (Symmetric HS256 là đủ đáp ứng)
  • Yêu cầu thu hồi quyền hạn tức thời đến từng giây (stateless JWT có độ trễ thu hồi bằng thời hạn hết hạn)
  • Dữ liệu Payload quá lớn (kích thước token phình to làm chậm network request)
  • Team chưa có kinh nghiệm quản lý hạ tầng lưu trữ khóa bí mật an toàn
