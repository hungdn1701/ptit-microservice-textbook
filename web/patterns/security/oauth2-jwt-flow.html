Act 01

The Problem

Trong Microservices, nếu mỗi request đều buộc các downstream services gọi đồng bộ về Auth DB để validate Session, Auth DB sẽ trở thành bottleneck. Ngoài ra, việc dùng chung khóa đối xứng (Symmetric Key) tiềm ẩn rủi ro lộ khóa bảo mật.

Bottleneck

Auth DB Bottleneck

Khi có hàng ngàn concurrent requests, việc gọi vào Auth DB để validate Session làm DB quá tải. Nếu Auth Service sập, toàn bộ các dịch vụ khác (kể cả public API) cũng bị block theo.

Security

Rủi ro từ Symmetric Key (Key Leak)

Với HS256, cả Auth Service (cấp token) và Resource API (verify token) dùng chung Secret Key. Nếu một microservice bị xâm nhập và lộ Secret Key, attacker có thể tự ký (forge) token với quyền ADMIN.

2
Act 02

The Pattern

Sử dụng Asymmetric Key **RS256**: Auth Service giữ **Private Key** để ký Token, các downstream services dùng **Public Key** để verify. Cấp phát theo cặp: **Access Token** (short-lived, VD: 15p) để gọi API và **Refresh Token** (long-lived, VD: 7d) dùng để xin cấp lại Access Token mà không cần user login lại.

— Token-based Authentication · OAuth 2.0 & RFC 7519 (JWT)

Cơ chế Decentralized Authentication qua chữ ký số (Digital Signature) giúp hệ thống hoàn toàn stateless: API tự verify token thông qua phép toán mã hóa thay vì gọi network về DB.

Thành phần 01
Thành phần 01

Authorization Server

Xác thực credentials và phát hành Access/Refresh Token bằng Private Key. Hỗ trợ Key Rotation định kỳ để đảm bảo an ninh.

Thành phần 02

Resource Server

API Gateway và microservices. Chúng fetch Public Key từ Auth và tự verify JWT chữ ký mà không cần network call (Zero-network Validation).

Thành phần 03

Refresh Token Flow

Khi Access Token hết hạn (Expired), Client gửi Refresh Token cho Auth Service. Auth Service validate Refresh Token trong DB và issue Access Token mới (Automatic refresh).

Act 04 — Case Study

KBM: Apply It

KBM chuyển từ HS256 sang RS256 để chống leo thang đặc quyền (Privilege Escalation) từ môi trường Judge Sandbox.

Đánh giá rủi ro và các giải pháp mã hóa chữ ký

Tiêu chí Cấu hình HS256 ban đầu Cấu hình RS256 đề xuất Mục đích an ninh
Thuật toán ký Symmetric (Mã hóa đối xứng) Asymmetric (Mã hóa bất đối xứng) Ngăn downstream services tự forge token.
Phân phối khóa Dùng chung Shared Secret. Auth giữ Private Key, Gateway & Services fetch Public Key. Kể cả khi bị leak Public Key, attacker không thể ký token.
Key Rotation Phức tạp (Requires restart). Dễ dàng (Auto-fetch qua JWKS). Automated key rotation (VD: 30 ngày) không gây downtime.

Lộ trình nâng cấp an ninh KBM

Các bước di chuyển luồng Auth sang RS256
Phase 1

Generate RSA Key Pair

Dùng OpenSSL tạo cặp RSA 2048-bit. Cấu hình kbm-auth load Private Key từ Secret Manager (Vault/KMS). Expose Public Key qua JWKS endpoint (/.well-known/jwks.json).

Phase 2

Configure Resource Server (Gateway)

Cấu hình Spring Security OAuth2 tại kbm-gateway để auto-fetch Public Key từ JWKS. Bật local token validation tại Gateway.

Phase 3

Implement Refresh Token Flow (Frontend)

Thêm Axios Interceptor: Khi nhận 401 Unauthorized, tự động gọi /oauth2/token bằng Refresh Token (HttpOnly Cookie) để lấy Access Token mới rồi retry request.

Phase 4

Token Blacklisting với Redis

JWT stateless khó thu hồi, nên KBM áp dụng Redis Blacklist. Khi Logout/Đổi mật khẩu, JWT ID (JTI) được push vào Redis với TTL bằng thời hạn còn lại của token.

Khi nào dùng — Khi nào không

✓
Nên dùng RS256 & OAuth2 khi
  • Hệ thống Microservices lớn có nhiều team phát triển độc lập.
  • Yêu cầu bảo mật cao, cần phân tách quyền cấp phát và xác thực token.
  • Cần hỗ trợ SSO (Single Sign-On) hoặc Identity Federation.
  • High throughput read requests, cần stateless validation phi tập trung.
✗
Không nên dùng khi
  • Monolith đơn giản (HS256 là đủ).
  • Hệ thống cần thu hồi quyền (Revoke) ngay lập tức mà không muốn maintain blacklist.
  • Payload quá lớn khiến JWT phình to, tăng network overhead.
  • Chưa có hạ tầng Secret Management (KMS, Vault).

Đọc chi tiết về OAuth2 Flow, Token JWT, thuật toán đối xứng/bất đối xứng, JWKS, và Secret Management trong sách.
