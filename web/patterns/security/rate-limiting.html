Act 01

Lũ lụt Request & Tấn công Brute-Force

Khi hệ thống mở rộng các API public ra ngoài internet, nếu không có cơ chế kiểm soát tần suất gửi request từ mỗi Client, dịch vụ sẽ rất dễ sụp đổ dưới sức ép của lượng truy cập bất thường, dù đó là vô ý hay cố ý tấn công.

⚡

Nghẽn tài nguyên cục bộ (Resource Exhaustion)

Các request spam gửi liên tục (ví dụ: quét dữ liệu, loop lỗi từ frontend) chiếm dụng hoàn toàn thread pool của web server và cạn kiệt bộ nhớ đệm CPU. Hệ thống Gateway bị đơ, không thể định tuyến request cho các người dùng hợp lệ khác.

🔒

Tấn công Brute-Force & Credential Stuffing

Kẻ xấu sử dụng botnet để thử hàng ngàn mật khẩu trên API đăng nhập (Auth endpoint). Nếu không giới hạn tốc độ gọi API, hacker không chỉ có cơ hội dò ra tài khoản mà còn làm tê liệt dịch vụ Authentication, sập toàn bộ hệ thống đăng nhập.

🚨

KBLab Incident — Sinh viên dùng script tự động cướp thread Gateway

Trong mùa làm bài tập lớn, một sinh viên viết script Python thực hiện vòng lặp vô hạn gọi API lấy kết quả chấm điểm từ kblab-judge với tần suất 10ms/request (100 request/giây) để hiển thị live score. Script chạy liên tục làm cạn kiệt kết nối Redis và Tomcat thread pool của kblab-gateway. Toàn bộ sinh viên khác bị chặn ngay ngoài Gateway với lỗi Gateway Timeout (504).

Act 02

Cơ chế lọc và giới hạn lưu lượng (Rate Limiter)

Đặt một bộ lọc lưu lượng (Filter) ngay tại API Gateway để đếm số request từ mỗi Client (dựa trên IP, API Key, hoặc User ID) trong một khoảng thời gian. Nếu tần suất vượt ngưỡng cho phép, Gateway từ chối xử lý ngay lập tức và trả về mã lỗi 429 Too Many Requests kèm HTTP header Retry-After.

— Rate Limiting Pattern · API Gateway Architecture

Thuật toán **Token Bucket** (Xô chứa Token) là giải pháp phổ biến nhất: một cái xô có dung lượng tối đa (Burst Capacity) được bổ sung token tự động theo tốc độ cố định (Replenish Rate). Mỗi request đi qua tiêu thụ 1 token. Nếu xô hết token, request bị block.

Thành phần 01

Key Resolver

Bộ định danh Client để áp dụng giới hạn. Có thể resolve theo: Địa chỉ IP (dành cho public route), User JWT (cho cá nhân), hoặc App ID (cho kết nối B2B/Partner).

Thành phần 02

Redis Shared State

Lưu trữ trạng thái xô token. Sử dụng Redis (thông qua lệnh Lua script nguyên tử) giúp đảm bảo giới hạn hoạt động chính xác khi triển khai nhiều instances Gateway chạy song song (Distributed Rate Limiting).

Thành phần 03

HTTP 429 Handler

Đánh dấu mã lỗi 429 và định cấu hình header X-RateLimit-Remaining (số token còn lại) và X-RateLimit-Reset (thời gian nạp đầy) để báo Client tự giãn cách.

Act 04

Thiết lập cấu hình KBLab Gateway

Áp dụng cấu hình Rate Limiting chi tiết tại kblab-gateway cho từng nhóm API route cụ thể để ngăn ngừa lạm dụng tài nguyên.

Cấu hình chi tiết các Endpoint KBLab

Quyết định cấu hình xô token dựa trên độ nhạy cảm của API
API Routes Key Resolver Replenish Rate Burst Capacity Mục đích bảo vệ
/api/v1/auth/login Client IP Address 1 token / 3 giây 5 tokens CRITICAL: Chống brute-force dò mật khẩu và spam đăng nhập ảo.
/api/v1/assignments/*/submit Student ID (JWT) 1 token / 5 giây 3 tokens HIGH: Chống submit bài thi liên tục gây quá tải Judge engine.
/api/v1/courses/** (Queries) Student ID (JWT) 10 tokens / giây 20 tokens MED: Đảm bảo sinh viên tải giao diện học mượt mà, hạn chế spam reload.
/static/** (Assets) Không áp dụng ∞ ∞ LOW: File tĩnh được cache tại CDN/Nginx, không cần rate limit ở Gateway.

Lộ trình triển khai Rate Limiting

Tiến trình triển khai an toàn từ Dev đến Production
Phase 1 · Tuần 1

Triển khai cụm Redis Shared Cache

Cài đặt cụm Redis cluster cho API Gateway. Cấu hình Spring Cloud Gateway sử dụng RedisRateLimiter. Viết class IpKeyResolver lấy IP Client chính xác đứng sau Nginx Proxy.

Dự kiến: 1 dev × 2 ngày
Phase 2 · Tuần 2

Thiết lập cấu hình Route YAML & Custom Header

Khai báo RequestRateLimiter filter cho từng route trong file application.yml. Cấu hình trả về custom header để client-side biết giới hạn còn lại và tự động delay.

✓ Tích hợp thành công filter giới hạn IP
Phase 3 · Tuần 3

Xây dựng Giao diện Thông báo 429 Thân thiện

Thay đổi phản hồi thô của JSON lỗi thành một giao diện HTML thông báo lịch sự cho người dùng khi bị rate limit, kèm đồng hồ đếm ngược chờ phục hồi trên Frontend.

Dự kiến: 1 dev × 3 ngày
Phase 4 · Tuần 4

Auto-scaling & Monitoring cảnh báo Spam

Đồng bộ metrics từ Redis và Gateway Actuator sang Prometheus. Thiết lập cảnh báo Grafana khi có IP bị trigger mã lỗi 429 liên tục (phát hiện dấu hiệu tấn công DDoS chủ động để tự động block IP tại Cloudflare/Nginx).

✓ Hệ thống phòng ngự Gateway hoàn tất

Khi nào dùng — Khi nào không

✅
Nên dùng Rate Limiting khi
  • Cung cấp API công khai (Public API) cho bên thứ ba hoặc client mobile/web
  • Endpoint nhạy cảm có chi phí tính toán đắt đỏ (như sinh báo cáo, tìm kiếm mờ, AI)
  • API đăng ký, đăng nhập, gửi mã OTP để chống brute-force và spam SMS
  • Bảo vệ tài nguyên Database tránh bị quét cạn kết nối
❌
Không nên dùng khi
  • Giao tiếp nội bộ giữa các microservice qua mạng riêng (Private Network) có độ tin cậy cao
  • Tải các file tĩnh (CSS, JS, Image) đã được tối ưu hóa qua cache CDN
  • Hệ thống đòi hỏi luồng nhận dữ liệu thời gian thực không giới hạn băng thông
  • Chưa có giải pháp Key Resolver chuẩn hóa (dễ dẫn đến block nhầm cả NAT IP mạng cơ quan)
