Act 01

The Problem

Khi hệ thống KBM LMS phát triển, kiến trúc Monolithic — nơi toàn bộ modules nằm trong cùng một deployment unit — bộc lộ nhiều hạn chế nghiêm trọng về khả năng scale, tốc độ triển khai, và tính độc lập của đội phát triển.

Perf Constraint

Deployment Bottleneck

Mỗi thay đổi nhỏ (ví dụ: sửa bug trong module Judge) đều yêu cầu rebuild và redeploy toàn bộ ứng dụng. Thời gian deploy tăng tuyến tính theo kích thước codebase.

Scale Limit

Scaling Constraint

Module kbm-judge-sql cần scale gấp 10× vào mùa thi, nhưng kiến trúc monolith buộc phải scale toàn bộ app — lãng phí tài nguyên cho Auth, Notification, Assignment vốn không cần thêm capacity.

Trade-off Comparison
Tiêu chí Monolith Microservices
Deploy speed ✗ Toàn bộ app ✓ Từng service
Scalability ✗ Scale cả khối ✓ Scale từng phần
Complexity ✓ Đơn giản ✗ Distributed
Data consistency ✓ ACID tự nhiên ✗ Saga / eventual
Team autonomy ✗ Coordination cao ✓ Deploy độc lập
Debugging ✓ Breakpoint trực tiếp ✗ Distributed tracing
Tech stack ✗ Đồng nhất ✓ Polyglot

Act 04 — Case Study

KBM: Apply It

Hệ thống KBM bắt đầu là một monolith Spring Boot duy nhất. Khi module Judge cần scale riêng vào mùa thi (xử lý SQL submission đồng thời), team buộc phải tách kbm-judge-sql ra thành microservice độc lập — đây là tín hiệu tự nhiên cho microservices decomposition.
