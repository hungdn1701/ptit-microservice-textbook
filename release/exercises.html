Chương 1: Monolith → Microservices

1-0 [NOTE] Ôn tập: Monolith vs Microservices [L1]

Ghép mỗi đặc điểm (cột trái) với kiến trúc phù hợp nhất (cột phải).

Câu hỏi thêm:

  1. Martin Fowler khuyên chiến lược gì khi bắt đầu dự án mới? Giải thích ngắn gọn lý do.
  2. Kể tên 3 dấu hiệu cho thấy một monolith đã sẵn sàng để tách microservices (tham khảo Bảng 1.1).
  3. So sánh cơ chế mở rộng (scaling) giữa kiến trúc Monolith và Microservices. Giải thích tại sao Microservices tối ưu tài nguyên phần cứng hơn khi hệ thống phải xử lý tải trọng không đồng đều giữa các tính năng.

1-1 [EVAL] Khi nào KHÔNG nên Microservices? [L2]

Tình huống: Người đọc trong vai chuyên gia tư vấn kiến trúc, được ba công ty mời tư vấn “có nên chuyển sang microservices?”

Câu hỏi phân tích:

  1. Áp dụng Ma trận quyết định (Bảng 10.1, Chương 10 — đọc trước phần này) cho từng công ty. Chấm điểm cụ thể cho mỗi tiêu chí?
  2. Tính Microservice Premium cho mỗi trường hợp: chi phí phải trả (độ phức tạp của hệ phân tán, mức trưởng thành DevOps cần có, thời gian học) so với lợi ích thực tế
  3. Đưa ra khuyến nghị cho mỗi công ty: Yes / Not Yet / Never — kèm lập luận cụ thể
  4. Cho công ty B (ứng viên mạnh nhất): service nào nên tách TRƯỚC? Vì sao? Áp dụng nguyên tắc “tách service mang lại nhiều giá trị nhất trước” (Richardson [2a, Ch.13])
  5. Câu hỏi ByteByteGo: Công ty A muốn người đọc thiết kế microservices “để sẵn cho tương lai”. Người đọc sẽ thuyết phục họ thế nào rằng đây là sai lầm? Dùng trích dẫn nào của Martin Fowler?

1-2 [CASE] Case Study: Shopify — Monolith tỷ đô [L3]

Bối cảnh: Shopify (2023) vận hành trên Ruby on Rails monolith phục vụ hàng triệu nhà bán hàng, xử lý $444 tỷ GMV. Thay vì chuyển sang microservices, Shopify chọn Modular Monolith — tách code thành các component có ranh giới rõ ràng nhưng deploy cùng nhau.

Tham khảo: Shopify Engineering Blog “Deconstructing the Monolith” (2019), “Under Deconstruction” (2020).

Câu hỏi phân tích:

  1. Tại sao Shopify — với quy mô lớn hơn hầu hết các công ty — lại KHÔNG chuyển sang microservices? Đây có mâu thuẫn với lời khuyên của Newman không?
  2. Modular Monolith khác gì Microservices về: (a) ranh giới triển khai, (b) cô lập dữ liệu, (c) chi phí giao tiếp (communication overhead), (d) quyền tự chủ của đội ngũ?
  3. Shopify dùng khái niệm Component Boundaries thay vì Service Boundaries. So sánh hai khái niệm này — khi nào component boundary đủ, khi nào cần service boundary?
  4. Nếu KBM trong sách áp dụng Modular Monolith thay vì Microservices, kiến trúc sẽ trông thế nào? Vẽ sơ đồ. Trade-offs so với kiến trúc hiện tại?
  5. Tranh luận: “Microservices là bắt buộc cho hệ thống lớn” — người đọc đồng ý hay phản đối? Dùng Shopify làm bằng chứng.

Chương 2: DDD & Bounded Contexts

2-0 [NOTE] Ôn tập: Các khái niệm Domain-Driven Design [L1]

Chọn định nghĩa đúng cho mỗi khái niệm DDD:

  1. Bounded Context là:

    • (a) Một cơ sở dữ liệu riêng cho mỗi service
    • (b) Ranh giới mà trong đó một mô hình domain có nghĩa nhất quán
    • (c) Một design pattern để tách frontend và backend

  2. Ubiquitous Language là:

    • (a) Ngôn ngữ lập trình chung cho toàn dự án
    • (b) Từ vựng thống nhất giữa lập trình viên và chuyên gia nghiệp vụ trong cùng một Bounded Context
    • (c) Tài liệu API specification bằng OpenAPI

  3. Aggregate là:

    • (a) Một cụm entity được xử lý như một đơn vị nhất quán (consistency boundary)
    • (b) Một bảng trong cơ sở dữ liệu quan hệ
    • (c) Một microservice chứa nhiều API endpoints

  4. Trong KBM, “bài nộp” (Submission) thuộc Bounded Context nào? “Tài khoản sinh viên” thuộc Context nào? Hai Context này giao tiếp qua cơ chế gì?

  5. Phân tích vai trò của chuyên gia nghiệp vụ (Domain Expert) trong việc xác định Bounded Context. Tại sao quá trình thiết kế hệ thống Microservices không nên chỉ do đội ngũ kỹ sư phần mềm thực hiện độc lập?

2-1 [DESIGN] Event Storming: Thiết kế Hệ thống Đăng ký Tín chỉ [L2]

Tình huống: Người đọc đang thiết kế hệ thống đăng ký tín chỉ (LMS Course Registration) cho học kỳ mới. Các bên liên quan mô tả:

Kịch bản

“Sinh viên đăng nhập hệ thống, tìm kiếm học phần mở trong kỳ. Hệ thống kiểm tra điều kiện tiên quyết. Sinh viên chọn lớp và nhấn đăng ký. Hệ thống kiểm tra sĩ số lớp, nếu còn chỗ sẽ ghi nhận đăng ký thành công và cập nhật sĩ số. Nếu lớp đầy, sinh viên được đưa vào danh sách chờ (waitlist). Khi đăng ký xong, hệ thống gửi thông tin sang phòng Tài vụ để tính học phí. Sinh viên phải hoàn thành đóng học phí trong 7 ngày, nếu không hệ thống sẽ tự động hủy kết quả đăng ký.”

Yêu cầu:

  1. Liệt kê Domain Events (≥12 sự kiện) theo trình tự: CourseSearched → PrerequisiteChecked → RegistrationRequested → ...
  2. Xác định Aggregates: nhóm các sự kiện → xác định ≥4 aggregate (Course? Registration? Waitlist? Payment? …)
  3. Vẽ Bounded Contexts: xác định ≥4 context và quan hệ giữa chúng
  4. Câu hỏi trade-off: Nên tách “Billing/Payment” thành bounded context riêng hay gộp vào “Registration Management”? Phân tích ưu nhược của cả hai cách
  5. Conway’s Law: Nếu đội chỉ có 8 người, người đọc tổ chức đội thế nào để khớp với các bounded context?

Chương 3: Thiết kế API

3-0 [NOTE] Ôn tập: Các nguyên tắc thiết kế API [L1]

Phân loại mỗi thay đổi API sau đây là Breaking hay Non-breaking:

Câu hỏi thêm:

  1. Giải thích nguyên tắc Tolerant Reader (Postel’s Law). Tại sao nguyên tắc này quan trọng cho việc phát triển API theo thời gian (API evolution)?
  2. REST API nên dùng chiến lược versioning nào: URL path (/v2/users) hay header (Accept: application/vnd.api+v2)? Nêu 1 ưu và 1 nhược cho mỗi cách.
  3. Đánh giá tầm quan trọng của việc duy trì tính tương thích ngược (backward compatibility) khi thiết kế API trong kiến trúc Microservices so với kiến trúc Monolith. Hậu quả của việc vi phạm nguyên tắc này là gì?

3-1 [CASE] Case Study: Stripe API — Tại sao được coi là “gold standard”? [L2]

Bối cảnh: Stripe API được cộng đồng lập trình viên đánh giá là API design tốt nhất thế giới. Phân tích tại sao.

Dữ liệu: Truy cập stripe.com/docs/api (hoặc dựa trên kiến thức).

Câu hỏi phân tích:

  1. Stripe dùng date-based versioning (2024-12-18) thay vì v1/v2. So sánh với URL path versioning — ưu/nhược điểm gì? Khi nào date-based tốt hơn?
  2. Stripe API trả response dạng envelope pattern: { "object": "list", "data": [...], "has_more": true }. So sánh với cách KBM trả { "data": [...], "pagination": {...} } — cái nào tốt hơn? Tại sao?
  3. Stripe sử dụng Idempotency Key cho mọi POST request (tránh trừ tiền khách hàng 2 lần). Thiết kế cơ chế tương tự cho POST /api/submissions của LMS — sinh viên nộp bài 2 lần do mạng chậm → chỉ chấm 1 lần
  4. Stripe luôn trả error object nhất quán — mọi lỗi đều nằm dưới khóa error, kèm ba trường type, code và message (ví dụ type: "card_error", code: "expired_card"). So sánh với định dạng lỗi hiện tại của LMS — khoảng trống ở đâu?
  5. Thiết kế: Nếu người đọc phải thiết kế API cho tính năng mới: “Giảng viên tạo kỳ thi → sinh viên đăng ký → nộp bài → bảng xếp hạng”, viết danh sách endpoint theo phong cách của Stripe

  5. ADR: Viết Architecture Decision Record cho quyết định: “Từ nay response của API chỉ được THÊM trường, không được XÓA hoặc ĐỔI TÊN trường”

Chương 5: Giao tiếp Bất đồng bộ

5-0 [NOTE] Ôn tập: Các khái niệm Kafka [L1]

Điền vào chỗ trống bằng thuật ngữ đúng: Topic, Partition, Consumer Group, Offset, Producer, Broker.

  1. là đơn vị logic để phân loại message (ví dụ: submissions, grading-results).
  2. Mỗi topic được chia thành nhiều để xử lý song song.
  3. là vị trí (số thứ tự) của message trong partition — consumer dùng nó để theo dõi đã đọc đến đâu.
  4. Nhiều consumer instances cùng thuộc một sẽ chia nhau các partitions — mỗi partition chỉ được 1 consumer trong group xử lý.
  5. là thành phần gửi messages vào topic.
  6. là server Kafka lưu trữ và phục vụ messages.

Câu hỏi thêm:

  1. Giải thích sự khác biệt giữa at-most-once, at-least-once, và exactly-once. Luồng xử lý bài nộp (submission pipeline) của KBM nên dùng loại nào? Tại sao?
  2. Khi nào nên tăng số partitions của một topic? Có rủi ro gì khi tăng quá nhiều?
  3. Kết quả chấm bài cần hiện lên màn hình sinh viên ngay khi có. So sánh ba cách đẩy kết quả tới trình duyệt — polling, Server-Sent Events và WebSocket — theo bốn tiêu chí: độ trễ, tải lên server, chiều giao tiếp, và độ phức tạp khi service chạy nhiều instance. Chọn một phương án cho KBM và nêu điều kiện nào sẽ khiến phương án đó không còn phù hợp.

5-1 [EVAL] Kafka vs RabbitMQ — Quyết định dựa trên gì? [L2]

Tình huống: 4 kịch bản khác nhau, mỗi kịch bản cần một message broker:

Câu hỏi phân tích:

  1. Cho mỗi kịch bản: chọn Kafka hay RabbitMQ? Giải thích bằng khác biệt kiến trúc (log-based vs queue-based)
  2. Kleppmann trong [7, Ch.11] giải thích: Kafka = “distributed commit log” (chỉ ghi nối, consumer tự quản lý offset). RabbitMQ = “message queue” (broker đẩy message, message bị xóa sau khi ack). Mô hình tư duy (mental model) này giúp ra quyết định thế nào?
  3. LinkedIn (nơi tạo ra Kafka) xử lý 7 nghìn tỷ message/ngày trên 7 triệu partition (số liệu 2019). Họ CẦN Kafka. KBM có nhiều loại queue khác nhau: submission pipeline, SQL Judge worker dispatch (judge → judge-*), DevOps Lab jobs. Luồng nào thật sự cần Kafka, luồng nào chỉ cần DB queue? Đánh đổi giữa “học đúng công cụ” và “dùng công cụ phù hợp”?
  4. Exactly-once delivery: Kafka hỗ trợ ngữ nghĩa exactly-once theo giao dịch từ bản 0.11. RabbitMQ không hỗ trợ exactly-once sẵn có. Giải thích tại sao exactly-once khó và tại sao “at-least-once + idempotent consumer” thường đủ
  5. KBM chọn Kafka cho luồng xử lý bài nộp. Nếu dùng RabbitMQ hoặc DB queue thay thế, kiến trúc thay đổi thế nào? Tính năng nào bị mất?

5-2 [DEBUG] Debugging: “Thông điệp biến mất” — Dead Letter & Poison Pills [L3]

Tình huống sự cố:

Triệu chứng

Triệu chứng: Kỳ kiểm tra cuối kỳ — 5 sinh viên báo “nộp bài nhưng không nhận kết quả”. Giảng viên kiểm tra DB: bản ghi bài nộp vẫn tồn tại, nhưng không có điểm.

Nhật ký điều tra:

  • Log của Core Service: ✓ sự kiện SubmissionCreated được publish thành công
  • Kafka topic submissions: ✓ Message vẫn tồn tại (đã kiểm tra bằng kafka-console-consumer)
  • Log của Judge Service: 5 message ném JsonParseException → consumer crash và khởi động lại → message được tiêu thụ lại → crash lại → vòng lặp vô hạn
  • Nguyên nhân gốc rễ: 5 bài nộp chứa SQL có ký tự Unicode đặc biệt → giải tuần tự hóa (deserialization) thất bại

Gợi ý

Xem lại khái niệm Dead Letter Topic ở Chương 5 và cấu hình @RetryableTopic.

Câu hỏi phân tích:

  1. Đây là ví dụ về message “Poison Pill”. Định nghĩa poison pill. Tại sao nó nguy hiểm hơn một message xử lý lỗi thông thường?

  2. Không có DLT (Dead Letter Topic): consumer crash → khởi động lại → tiêu thụ lại chính message đó → crash → lặp vô hạn. 45 message khác (của các sinh viên không gặp lỗi) cũng bị kẹt phía sau poison pill. Giải thích cơ chế (offset của Kafka consumer không được commit khi xử lý lỗi)

  3. Thiết kế giải pháp 3 tầng:

    • Tầng 1: Retry (bao nhiêu lần? chiến lược backoff?)
    • Tầng 2: Dead Letter Topic (định dạng message? cơ chế cảnh báo?)
    • Tầng 3: Dashboard rà soát thủ công (admin xem các message trong DLT, xử lý lại hoặc loại bỏ)

  4. Sau khi triển khai DLT, luồng xử lý mới sẽ như thế nào? Vẽ sơ đồ. 5 message lỗi đi đâu? 45 message còn lại có bị ảnh hưởng?

  5. Phòng ngừa: Làm sao ngăn poison pill ngay từ đầu? (kiểm tra schema, contract testing ở producer)

6-1 [DESIGN] Design: Uber Ride Saga — Choreography hay Orchestration? [L3]

Tình huống: Một chuyến xe Uber trải qua các bước:

1. Rider request ride
2. Match driver (tìm tài xế gần nhất)
3. Driver accept
4. Trip starts (GPS tracking bắt đầu)
5. Trip ends (tính khoảng cách)  
6. Calculate fare (surge pricing, discounts)
7. Charge rider's payment method
8. Pay driver (sau commission)
9. Send receipt

Nếu bước 7 thất bại (thẻ hết tiền):

Compensation: Cancel payment → Notify rider "add payment method" → Hold trip record (chờ retry)
NHƯNG: KHÔNG thể undo trip (đã chạy rồi!) → Đây là "non-compensatable action"

Câu hỏi phân tích:

  1. Xác định compensable, pivot, và retriable transactions trong 9 bước. Bước nào là điểm không thể quay lui (point of no return)?
  2. Uber (thực tế) dùng Orchestration cho ride saga — tại sao? So sánh nếu dùng Choreography: cần bao nhiêu sự kiện? Ai theo dõi trạng thái tổng thể?
  3. Vấn đề isolation: Khách A đặt xe, tài xế X được ghép → trong lúc tài xế X đang trên đường đến → khách B đặt xe, hệ thống cũng ghép tài xế X. Đây là anomaly gì? (Lost update? Dirty read?) Biện pháp đối phó (countermeasure) nào cho kịch bản này?
  4. Thiết kế timeout: Tài xế không nhận chuyến trong 30 giây → timeout → tìm tài xế khác. Nhưng do mạng chậm, tài xế nhận chuyến ở giây thứ 31 (message đến trễ). Thiết kế cơ chế xử lý “nhận chuyến muộn” (late acceptance)
  5. Liên hệ KBM: Hãy thiết kế Saga cho Quy trình nộp học phí: Sinh viên nộp tiền → Hệ thống ngân hàng báo thành công → Cập nhật công nợ → Mở khóa tài khoản đăng ký tín chỉ. Nếu bước mở khóa lỗi, quy trình bù trừ (hoàn tiền hoặc bảo lưu) sẽ thực hiện thế nào? Vẽ sơ đồ.

6-2 [EVAL] Trade-off: Choreography vs Orchestration [L2]

Bài tập: Cho 4 kịch bản saga, phân tích nên dùng Choreography hay Orchestration:

Câu hỏi phân tích:

  1. Cho mỗi saga: Choreography hay Orchestration? Lập luận dựa trên độ phức tạp, số bước, xác suất lỗi, mức độ tham gia của con người
  2. Richardson nói “≤4 steps → Choreography OK, >4 steps → consider Orchestration”. Người đọc có đồng ý không? Có ngoại lệ không?
  3. Saga D (Đặt vé máy bay) đặc biệt khó — các API bên ngoài (hãng bay, khách sạn) có thể timeout hoặc trả kết quả mơ hồ. Thiết kế bù trừ cho tình huống: “Đặt chặng 1 thành công, đặt chặng 2 bị timeout — không biết thành công hay thất bại”. Đây là “trạng thái không chắc chắn” (uncertain state) — xử lý thế nào?
  4. Netflix dùng Conductor (engine orchestration mã nguồn mở). Uber dùng Cadence/Temporal. Tại sao các công ty lớn tự xây engine orchestration riêng thay vì dùng choreography?

7-1 [EVAL] CAP Theorem trong Thực tế — “Pick Two” có đúng không? [L3]

Tình huống: Đội ngũ tranh luận về chiến lược database:

Kịch bản

“CAP theorem nói chỉ chọn được 2 trong 3: Consistency, Availability, Partition Tolerance. Vậy nếu partition xảy ra, ta phải chọn giữa C và A. Nhưng hệ thống của ta cần CẢ HAI…”

Câu hỏi phân tích:

  1. Martin Kleppmann phản bác cách hiểu “pick two”. Ông nói CAP thực ra là: “During a network partition, choose between consistency and availability. When there’s NO partition, you can have both.” Giải thích — khác biệt thực tế so với “pick two” là gì?
  2. Phân loại các database theo CAP:

  1. KBM dùng PostgreSQL cho nhiều dữ liệu giao dịch. Khi primary DB down một khoảng thời gian, hệ thống có thể không khả dụng cho các luồng ghi. Nếu dùng PostgreSQL với streaming replication, trade-off thay đổi thế nào?

  2. Kịch bản trong trường học: Giỏ đăng ký môn học dự kiến vs Thanh toán học phí — yêu cầu C/A khác nhau:

    • Giỏ môn học: availability > consistency (OK nếu rớt mạng vẫn lưu tạm, có thể thêm bớt sau)
    • Thanh toán học phí: consistency > availability (KHÔNG OK nếu trừ tiền 2 lần)
    • Thiết kế: dùng database strategy nào cho từng tính năng?

  3. Câu hỏi ByteByteGo: Bài báo Dynamo của Amazon (SOSP 2007) nêu yêu cầu cho dịch vụ giỏ hàng: “customers should be able to view and add items to their shopping cart even if disks are failing, network routes are flapping, or data centers are being destroyed by tornados.” Vì vậy giỏ hàng dùng kho lưu trữ eventually consistent (Dynamo) và chấp nhận có lúc phải hợp nhất các phiên bản giỏ hàng xung đột. Người đọc có đồng ý với trade-off này không? Giải thích bằng CAP

7-2 [DESIGN] Design: Chiến lược chuyển đổi database cho KBM [L2]

Tình huống: KBM hiện có shared database — Core Service và Assignment Service dùng chung PostgreSQL. Người đọc được giao nhiệm vụ tách database.

Ràng buộc:

  • Zero downtime (sinh viên đang dùng hệ thống)
  • Đội ngũ 2 lập trình viên
  • Thời gian: 3 tháng
  • Không được mất dữ liệu

Các bảng:

Core domain:     questions, submissions, scores, contests
Assignment domain: assignments, assignment_questions, student_assignments
Shared:          users (dùng bởi CẢ HAI)
Cross-reference: assignment_questions.question_id → questions.id

Câu hỏi phân tích:

  1. Áp dụng 5 chiến lược tách database (§7.2, Hình 7.5): thiết kế lộ trình 3 tháng — tháng 1, 2, 3 làm gì?
  2. Bảng users được cả hai service sử dụng. 3 phương án: (a) giữ ở Core, Assignment gọi API, (b) nhân bản dữ liệu users, (c) tạo User Service riêng. Phân tích trade-off của từng phương án
  3. assignment_questions tham chiếu questions.id — đây là một phép join xuyên miền (cross-domain join). Sau khi tách DB, join này KHÔNG CÒN HOẠT ĐỘNG. Thiết kế giải pháp: API composition? Data duplication? CQRS?
  4. Rủi ro ghi kép (dual write): Trong quá trình chuyển đổi, có một giai đoạn code cũ (truy cập DB trực tiếp) và code mới (qua API) cùng tồn tại. Làm sao tránh dữ liệu không nhất quán? (Feature flag? Shadow write?)
  5. Kế hoạch rollback: Nếu tháng 2 phát hiện vấn đề hiệu năng nghiêm trọng — làm cách nào để rollback về shared database an toàn?

8-1 [CASE] Case Study: Netflix Zuul 1 → Zuul 2, và Spring Cloud Gateway [L2]

Bối cảnh: Netflix viết lại API Gateway của mình từ blocking sang non-blocking; hệ sinh thái Spring đi một hướng riêng:

Zuul 1
(mã nguồn mở năm 2013): Blocking I/O, dựa trên servlet, mỗi request chiếm một thread
Zuul 2
(Netflix giới thiệu năm 2016, mã nguồn mở năm 2018): Non-blocking, dựa trên Netty. Năm 2018, Netflix vận hành hơn 80 cluster Zuul 2, xử lý hơn 1 triệu request/giây, làm cửa ngõ cho mọi request vào hạ tầng cloud của Netflix
Spring Cloud Gateway
(bản chính thức đầu tiên năm 2018, trong Spring Cloud Finchley): Dự án của Spring, không phải của Netflix; reactive trên Spring WebFlux và Reactor Netty; được Spring giới thiệu là gateway thế hệ mới thay thế Spring Cloud Netflix Zuul

Câu hỏi phân tích:

  1. Chuyển từ Zuul 1 sang Zuul 2 nghĩa là viết lại gateway theo mô hình bất đồng bộ. Cái giá của việc này là gì (độ phức tạp khi lập trình, khi gỡ lỗi, các thư viện đi kèm cũng phải bất đồng bộ)? Vì sao một hệ thống ở quy mô Netflix vẫn chấp nhận trả cái giá đó? (Gợi ý: đọc bài “Zuul 2: The Netflix Journey to Asynchronous, Non-Blocking Systems”, Netflix TechBlog, 2016)
  2. Blocking vs Non-blocking Gateway: Zuul 1 dùng 1 thread/request (blocking). Spring Cloud Gateway dùng event loop (non-blocking). Với 10K kết nối đồng thời, Zuul 1 cần bao nhiêu thread? Spring Cloud Gateway cần bao nhiêu? Hệ quả với bộ nhớ?
  3. KBM dùng Spring Cloud Gateway cho LMS core và Go hostname-based router cho DevOps Lab. Với lưu lượng học thuật vừa phải, blocking hay non-blocking có khác biệt? Khi nào KBM CẦN non-blocking gateway/router?
  4. Gateway là điểm lỗi duy nhất (single point of failure): Nếu Gateway sập, toàn bộ hệ thống ngừng hoạt động. Thiết kế tính sẵn sàng cao cho Gateway thế nào? (Nhiều instance? Load balancer phía trước?)
  5. BFF Pattern (Backend for Frontend): Netflix có gateway riêng cho ứng dụng mobile (băng thông ít) và ứng dụng web (cần nhiều dữ liệu hơn). Nếu KBM cần hỗ trợ ứng dụng mobile, người đọc sẽ thiết kế BFF thế nào?

9-1 [DEBUG] Sự cố bảo mật: Đánh cắp JWT token [L3]

Tình huống sự cố:

Báo cáo

Báo cáo: Sinh viên A phát hiện điểm bài tập thay đổi — bài chưa nộp bỗng có điểm 100. Log cho thấy các bài nộp được tạo bằng JWT token của sinh viên A, nhưng từ một địa chỉ IP khác.

Điều tra: Sinh viên B (cùng phòng) sao chép JWT token từ DevTools trên trình duyệt của A khi A quên đăng xuất trên máy dùng chung. Token dùng HS256, thời hạn 24 giờ, không có cơ chế làm mới token (refresh).

Câu hỏi phân tích:

  1. Tại sao JWT stateless lại nguy hiểm trong tình huống này? Token bị đánh cắp nhưng server không biết — không có cơ chế thu hồi (revoke). So sánh với xác thực dựa trên session (session ID có thể thu hồi ngay lập tức)

  2. Các tầng giảm thiểu rủi ro — thiết kế 4 tầng bảo vệ:

    • Tầng 1: Thời hạn sống của token (TTL): rút ngắn thời hạn → bao nhiêu phút là hợp lý?
    • Tầng 2: Làm mới và xoay vòng token (refresh + rotation) (Ch.9, Listing 9.1) — giải thích tại sao xoay vòng giúp phát hiện token bị đánh cắp
    • Tầng 3: Nhận dạng thiết bị (device fingerprinting): gắn token với thiết bị/trình duyệt
    • Tầng 4: Phát hiện bất thường (anomaly detection): nộp bài từ 2 IP khác nhau trong 5 phút → gắn cờ

  3. HS256 vs RS256: (a) Sinh viên B đánh cắp được một JWT bearer token. B có thể dùng token này để truy cập hệ thống không? B có thể tự tạo token giả với vai trò ADMIN không? Trả lời cho cả hai trường hợp HS256 và RS256. (b) Nâng cao: Khác biệt nghiêm trọng hơn xuất hiện khi một service phía sau (downstream) bị xâm nhập — nếu service giữ khóa bí mật dùng chung (shared secret) của HS256 thì kẻ tấn công có thể tự ký token bất kỳ; nếu service chỉ giữ public key của RS256 thì sao? Phân tích phạm vi thiệt hại (blast radius) của từng trường hợp.

  4. Danh sách đen token (token blacklist): Triển khai danh sách đen (Redis set) để thu hồi các token bị đánh cắp. Trade-off: mất ưu điểm “stateless” của JWT. Khi nào danh sách đen đáng để đánh đổi?

  5. Zero Trust và tin cậy phân tầng (tiered trust): Tại sao mạng nội bộ (private network) không phải là bằng chứng danh tính? Đối chiếu rủi ro đang được chấp nhận (accepted risk) của KBM hiện nay (tin vào header thuần — plain-header trust — và tự viết mã phân tích JWT) với mục tiêu Tier 1 (signed proof đúng audience + local authorization). Đề xuất thứ tự chuyển đổi không làm gián đoạn các request đang đi qua Gateway.

Câu hỏi phân tích:

  1. Với mỗi ứng dụng (A-D): chọn OAuth2 flow nào? (Authorization Code + PKCE, Client Credentials, Device Authorization Grant)
  2. App A (SPA): Tại sao Authorization Code flow cần PKCE cho SPA? Không có PKCE → kiểu tấn công nào có thể xảy ra?
  3. App C (server-to-server): Client Credentials flow chỉ định danh workload, không tạo subject là người dùng. Nếu Judge Service cần xử lý thay mặt sinh viên, hãy thiết kế cơ chế delegation có chữ ký, tách subject khỏi actor, giới hạn audience/thời hạn, và nêu cách service đích phân quyền cục bộ (local authorization).
  4. KBM dùng token exchange: nhà cung cấp định danh bên ngoài/QLĐT/tên đăng nhập-mật khẩu → KBM JWT. Nếu chuyển sang Keycloak hoặc Microsoft Entra ID làm IdP trung tâm: những gì thay đổi? Lợi ích? Chi phí chuyển đổi?

Chương 10: Chuyển đổi Thực tế

10-0 [NOTE] Ôn tập: Các chiến lược chuyển đổi [L1]

Sắp xếp các bước sau đây của Strangler Fig Pattern theo thứ tự đúng:

Các bước (chưa đúng thứ tự):

  • (A) Chuyển hướng traffic từ tính năng cũ sang service mới
  • (B) Xác định tính năng ít rủi ro nhất để tách trước
  • (C) Xây dựng service mới hiện thực tính năng đã chọn
  • (D) Gỡ bỏ code cũ khỏi monolith sau khi service mới ổn định
  • (E) Chạy song song (canary/shadow) để so sánh kết quả cũ vs mới

Câu hỏi thêm:

  1. Nêu 2 anti-pattern phổ biến khi chuyển đổi từ monolith sang microservices (tham khảo Phụ lục D).
  2. Đúng hay Sai: “Nên tách tất cả services cùng lúc (Big Bang) để tiết kiệm thời gian.” Giải thích.
  3. KBM nên tách service nào trước? Tại sao? (Gợi ý: xem xét độ độc lập và giá trị nghiệp vụ)

10-1 [CASE] Case Study: Amazon — Monolith → SOA → Microservices (2002–2020) [L3]

Bối cảnh: Chỉ thị nổi tiếng được cho là của Jeff Bezos, ban hành khoảng năm 2002 (theo Steve Yegge kể lại trong “Stevey’s Google Platforms Rant”, 2011; trích một phần):

Trích dẫn

“All teams will henceforth expose their data and functionality through service interfaces. … There will be no other form of interprocess communication allowed … Anyone who doesn’t do this will be fired.”

Câu hỏi phân tích:

  1. Chỉ thị năm 2002 ra đời TRƯỚC khi thuật ngữ “microservices” phổ biến (bài viết của Lewis và Fowler, 2014). Amazon gọi kiến trúc của họ là “Service-Oriented Architecture”. Sự khác biệt giữa SOA của Amazon và microservices hiện đại là gì?
  2. Amazon không làm “big bang” rewrite. Họ tách service dần dần qua nhiều năm. Có thể dùng Strangler Fig Pattern (Ch.10) để mô tả quá trình này không? Vẽ lịch trình 3 giai đoạn
  3. Quy tắc “Two-Pizza Team” — mỗi team 6-8 người, sở hữu 1-2 service. Đây có phải là Conway’s Law trong thực tế? Liên hệ với Ch.2 (cấu trúc team ↔ ranh giới service)
  4. Amazon hiện có hàng nghìn microservices. Vấn đề mới: số service phình to mất kiểm soát (service sprawl), quản lý phụ thuộc, mơ hồ về quyền sở hữu. Giải pháp? (Service mesh, service catalog, platform team)
  5. So sánh với KBM: KBM có nhiều service/module cho một team nhỏ. Áp dụng quy tắc Two-Pizza: bao nhiêu service là hợp lý cho quy mô team này? KBM có rủi ro “quá nhiều service so với một team nhỏ” không?

10-2 [EVAL] Outbox Pattern vs Event Sourcing vs Change Data Capture [L2]

Tình huống: Team cần giải quyết vấn đề ghi kép (dual-write problem): vừa lưu DB vừa phát event. Có 3 cách tiếp cận:

Câu hỏi phân tích:

  1. So sánh 3 cách tiếp cận theo 6 tiêu chí: độ phức tạp, chi phí hạ tầng, độ trễ, độ tin cậy, thời gian học, tác động lên mô hình dữ liệu
  2. Event Sourcing thay đổi tận gốc mô hình dữ liệu (event là gốc, trạng thái được suy ra). Khi nào trade-off này đáng? Khi nào quá mức? Cho ví dụ domain phù hợp (ngân hàng) và không phù hợp (trang quản trị CRUD)
  3. CDC chạy bên ngoài mã ứng dụng — không cần thay đổi code. Ưu điểm rõ ràng. Nhưng nhược điểm là gì? (phụ thuộc loại DB, phức tạp khi vận hành, nhạy cảm với thay đổi schema)
  4. LMS chọn Outbox Pattern (Polling Publisher). Có hợp lý không? Nếu traffic tăng 100 lần, cách tiếp cận nào phù hợp hơn?
  5. Câu hỏi ByteByteGo: Người đọc đang phỏng vấn. Người phỏng vấn hỏi: “Giải thích vấn đề ghi kép (dual-write) và 3 cách giải quyết, mỗi cách kèm một ví dụ thực tế.” — Trả lời trong 3 phút

10-3 [DESIGN] Design: Đồng bộ dữ liệu và Strangler Fig [L3]

Tình huống: Người đọc đang áp dụng Strangler Fig Pattern để bóc tách tính năng “Điểm danh sinh viên” từ hệ thống Monolith cũ sang một Microservice mới. Tuy nhiên, tính năng “Tính điểm chuyên cần” vẫn nằm bên trong Monolith và cần dữ liệu điểm danh.

Câu hỏi phân tích:

  1. Nếu Service Điểm danh ghi dữ liệu vào Database mới, làm thế nào Monolith lấy được dữ liệu này để tính điểm?

  2. Phân tích trade-off của 3 phương án đồng bộ:

    • (A) Trigger ở Database mới đồng bộ ngược về DB Monolith.
    • (B) Tạo API trên Service mới để Monolith gọi đồng bộ (Sync API).
    • (C) Sử dụng Event Queue (Kafka/RabbitMQ) để Service mới gửi event AttendanceRecorded và Monolith hoạt động như Consumer lắng nghe.
  3. Kịch bản: Quá trình chuyển đổi kéo dài 6 tháng. Giữa chừng, trường thay đổi logic quy định thời gian điểm danh trễ. Việc duy trì logic này ở cả code Monolith lẫn Microservice tạo ra nguy cơ gì? Giải quyết thế nào?

11-1 [DEBUG] Debugging: Bí ẩn độ trễ tăng đột biến [L3]

Tình huống sự cố:

Cảnh báo

Cảnh báo: Dashboard Grafana báo độ trễ P99 của việc nộp bài tăng từ 2s → 12s. Xảy ra mỗi thứ Ba lúc 14:00.

Dữ liệu hiện có:

  • Metrics: CPU của tất cả service < 30%. Bộ nhớ bình thường. Kafka consumer lag tăng lúc 14:00.
  • Logs: Không có lỗi. Judge Service log: “Executing SQL…” — bình thường.
  • Tracing: Một trace mẫu cho thấy: Gateway (5ms) → Core (20ms) → Kafka publish (10ms) → Judge receive (delay 8000ms!) → Judge execute (800ms) → Core result (15ms)

Manh mối: Thứ Ba 14:00 = đầu giờ “Cơ sở dữ liệu” — 120 sinh viên truy cập hệ thống cùng lúc.

Câu hỏi phân tích:

  1. Từ dữ liệu trace, điểm nghẽn ở đâu? Kafka consumer delay 8000ms — nguyên nhân có thể là gì? (Gợi ý: consumer lag, số partition, số consumer thread)
  2. RED analysis: tính Rate, Error rate, Duration tại thời điểm xảy ra sự cố. Metric nào bất thường?
  3. Judge Service xử lý từng message tuần tự (chỉ một consumer thread). 120 bài nộp cùng lúc → dồn ứ trong hàng đợi. Thiết kế chiến lược mở rộng: (a) tăng số consumer thread/instance, (b) tăng số partition, (c) cả hai? Trade-off?
  4. Thiết kế SLO cho độ trễ nộp bài. Hiện P99 bình thường là 2s, lúc tăng đột biến là 12s. SLO hợp lý: “99% bài nộp < Xs” — X bao nhiêu? Ngưỡng cảnh báo?
  5. Nếu người đọc là kỹ sư trực (on-call) nhận cảnh báo lúc 14:05: mô tả runbook — 5 bước đầu tiên cần kiểm tra (từ tổng thể → chi tiết)?

Câu hỏi phân tích:

    • Startup 5 người, ngân sách $0-100/tháng
    • Scale-up 20 người, ngân sách $500/tháng, SLA 99.9%

12-1 [EVAL] Docker Compose vs Kubernetes — Ở quy mô nào? [L2]

Tình huống: 3 hệ thống ở các quy mô khác nhau:

Câu hỏi phân tích:

  1. Với mỗi hệ thống: Docker Compose hay Kubernetes? Hay kết hợp cả hai? Giải thích dựa trên các tiêu chí: năng lực team, chi phí vận hành, nhu cầu mở rộng
  2. Anti-pattern: Hệ thống A (3 service, 2 lập trình viên) muốn dùng Kubernetes “để sẵn cho tương lai”. Tính chi phí của Kubernetes cho team 2 người: thời gian học, bảo trì cluster, độ phức tạp khi debug. Chi phí > lợi ích?
  3. Lộ trình chuyển đổi (migration path): Hệ thống B (KBM) hiện dùng Docker Compose cho LMS core và k3s/Sysbox cho DevOps Lab. Khi nào CẦN mở rộng Kubernetes cho nhiều phần hơn? Xác định 3 tín hiệu kích hoạt (traffic, quy mô team, yêu cầu SLA)
  4. Managed vs Self-managed K8s: GKE/EKS/AKS so với tự dựng cluster bằng kubeadm. So sánh chi phí cho hệ thống C? So sánh rủi ro?
  5. Câu hỏi ByteByteGo: “How does Kubernetes ensure zero-downtime deployment?” — Trả lời: cơ chế Rolling Update, readiness probe, PDB (Pod Disruption Budget). Vẽ sơ đồ

12-2 [DESIGN] Design: CI/CD Pipeline cho Microservices [L3]

Tình huống: Người đọc cần thiết kế CI/CD pipeline cho KBM (Java LMS core nhiều repo/service + DevOps Lab Go multi-binary):

Yêu cầu:

  • Push code → tự động build → test → deploy lên staging → phê duyệt thủ công → deploy lên production
  • Chỉ build/test services bị thay đổi (không build lại toàn bộ)
  • Migration cơ sở dữ liệu chạy TRƯỚC khi deploy service
  • Cơ chế rollback: quay lại phiên bản trước trong < 5 phút
  • Quản lý secret: không hardcode mật khẩu trong cấu hình CI

Câu hỏi phân tích:

  1. Thiết kế pipeline: vẽ sơ đồ CI/CD pipeline với đầy đủ các stage, gồm: phát hiện service thay đổi, build song song, cổng kiểm thử (test gate), cổng phê duyệt, triển khai
  2. Phát hiện service thay đổi (nếu gom các service vào một mono-repo): Git diff → xác định service nào thay đổi → chỉ build service đó. Thiết kế thuật toán. Trường hợp biên: thư viện dùng chung thay đổi → build lại TẤT CẢ service?
  3. Thứ tự migration cơ sở dữ liệu: Core Service phụ thuộc vào các bảng dùng chung. Assignment Service phụ thuộc vào các bảng của Core. Thứ tự migration có quan trọng không? Thiết kế đồ thị phụ thuộc (dependency graph) cho các migration
  4. Chiến lược rollback: Dùng canary deployment cho production. Nếu instance canary có tỷ lệ lỗi > 5% → tự động rollback. Thiết kế cơ chế (health check → metrics → quyết định → rollback). Vẽ sơ đồ?
  5. GitOps vs push-based: CI/CD truyền thống chủ động đẩy (push) bản triển khai; GitOps (ArgoCD) kéo (pull) trạng thái mong muốn từ Git. So sánh trong bối cảnh LMS — nên dùng cách nào?

Capstone: Phỏng vấn thiết kế hệ thống — Thiết kế “Online Judge” [L3]

Đề bài (dạng phỏng vấn 45 phút):

Kịch bản

“Thiết kế hệ thống Online Judge (như LeetCode/HackerRank) cho 10.000 người dùng đồng thời. Hệ thống cho phép: người dùng nộp code (Python, Java, SQL), hệ thống chạy code trong sandbox, so sánh output, trả kết quả. Có chế độ thi (1.000 người dùng nộp bài cùng lúc) với bảng xếp hạng thời gian thực.”

Gợi ý cấu trúc câu trả lời (theo khung phỏng vấn system design):

  1. Làm rõ yêu cầu (5 phút): Yêu cầu chức năng? Phi chức năng (độ trễ, thông lượng, tính sẵn sàng)? Quy mô?

  2. Thiết kế tổng quan (10 phút): Vẽ sơ đồ kiến trúc. Xác định các service, database, message queue

  3. Đi sâu (20 phút): Chọn 2-3 thành phần quan trọng nhất:

    Thực thi trong sandbox
    Mỗi bài nộp một Docker container? Bảo mật? Giới hạn tài nguyên?
    Quản lý hàng đợi
    Chiến lược chia partition Kafka để lập lịch công bằng (chế độ thi)?
    Bảng xếp hạng
    CQRS + Redis sorted set? Tần suất cập nhật?

  4. Mở rộng và trade-off (10 phút):

    • 1.000 bài nộp đồng thời → chiến lược mở rộng Judge Service?
    • Trade-off CAP cho bảng xếp hạng: thời gian thực (eventual consistency) hay chính xác (strong consistency)?
    • Ước tính chi phí: mỗi bài nộp = 1 Docker container × 10 giây = tốn bao nhiêu tài nguyên tính toán?

Tiêu chí đánh giá:

  • ☐ Kiến trúc có ≥4 service rõ ràng
  • ☐ Kiểu giao tiếp hợp lý (đồng bộ hay bất đồng bộ, khi nào dùng gì)
  • ☐ Chiến lược quản lý dữ liệu (database-per-service, CQRS cho bảng xếp hạng)
  • ☐ Các resilience pattern (circuit breaker cho Judge, DLT cho các bài nộp thất bại)
  • ☐ Bảo mật (cô lập sandbox, xác thực bằng JWT)
  • ☐ Phân tích khả năng mở rộng (mở rộng ngang Judge Service, chiến lược chia partition)
  • ☐ Thảo luận trade-off (phân tích rõ ≥3 trade-off)
