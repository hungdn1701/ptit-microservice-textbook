Act 01

The Problem

Khi request đi qua chuỗi microservices (qua HTTP và Message Queue), việc theo vết trở nên khó khăn do logs bị phân mảnh ở từng container độc lập, thiếu context tương quan.

Logs

Isolated Logs

Khi xảy ra "Gateway Timeout", Gateway báo lỗi 504, nhưng kbm-core vẫn đang xử lý, và kbm-judge-sql chứa hàng ngàn dòng test case concurrent. Không thể correlate log nào thuộc về submission đang lỗi.

Latency

Latency Bottleneck Debugging

Hệ thống phản hồi mất 5 giây. Khó xác định nguyên nhân: Gateway quá tải, Kafka latency cao, Judge compute nặng, hay PostgreSQL DB lock. Việc phân tích hiệu năng bế tắc khi thiếu dữ liệu correlation.

Act 02

The Pattern

Gán định danh duy nhất (**Trace ID**) cho request tại Gateway. Trace ID được propagate qua các service boundaries (HTTP/Kafka Headers). Mỗi đơn vị công việc sinh ra một **Span** (Span ID, Parent Span ID). Spans được thu thập và trực quan hóa dưới dạng Waterfall.

— Distributed Tracing Pattern · Dapper (Google Research - 2010)

Pattern này biến logs phân mảnh thành hierarchical tree rõ ràng, thể hiện mối quan hệ cha-con và execution time của từng công việc.

Khái niệm 01

Trace ID & Span ID

Trace ID là định danh duy nhất cho toàn bộ request flow. Span ID định danh cho từng service hop. Parent Span ID giúp xây dựng hierarchical tree.

Khái niệm 02

Context Propagation

Cơ chế truyền Trace ID qua network boundaries. Sử dụng W3C Trace Context (traceparent header) hoặc B3 propagation, tự động inject bởi HTTP/Kafka clients.

Khái niệm 03

Trace Collector (Zipkin / Jaeger)

Thu thập Trace Spans bất đồng bộ từ các microservices. Cung cấp UI trực quan (Waterfall chart) để phân tích lỗi và latency của từng hop.

Act 04 — Case Study

KBM: Apply It

Tích hợp Distributed Tracing giúp KBM giám sát toàn bộ end-to-end traffic và detect latency bottlenecks realtime.

Observability Maturity Levels

So sánh các cấp độ log monitoring
Model Log Collection Latency Debugging Integration Complexity Infra Requirements
Cấp độ 1: Isolated Logs Logs lưu cục bộ trên container. Impossible (Dò thủ công). None None
Cấp độ 2: Centralized Logs Centralized logs qua Elasticsearch/Kibana. Khó (chỉ search qua keywords). Medium ELK stack hoặc Grafana Loki.
Cấp độ 3: Distributed Tracing Trace ID bám sát request flow, hiển thị Waterfall chart. Easy (Xác định bottleneck qua UI). High (Tích hợp Micrometer Tracing). Zipkin Server hoặc Jaeger + Prometheus.

Observability Implementation Roadmap

Các bước triển khai distributed tracing trên Production
Phase 1 · Tuần 1

Tích hợp Micrometer Tracing

Add dependencies micrometer-tracing-bridge-otel và OpenTelemetry exporter. Cấu hình log format tự động inject [traceId, spanId].

Dự kiến: 1 dev
Phase 2 · Tuần 2

Deploy Trace Collector (Zipkin/Jaeger)

Deploy Zipkin/Jaeger container. Cấu hình services gửi trace spans async qua HTTP để tránh overhead vào request thread.

✓ Trực quan hóa waterfall thành công
Phase 3 · Tuần 3

Context Propagation via Kafka & OpenFeign

Cấu hình OpenFeign Interceptor tự động inject traceparent header. Cấu hình KafkaTemplate truyền trace metadata qua message headers.

Dự kiến: 1 dev
Phase 4 · Tuần 4

Grafana Dashboard (Logs & Traces Correlation)

Tích hợp Grafana Loki và Tempo. Hỗ trợ pivot trực tiếp từ log line sang Trace Waterfall để phân tích root cause.

✓ Full Observability achieved

Decision Guide

Yes
Recommended When
  • Hệ thống microservices phức tạp, request path qua ≥ 3 services
  • Hệ thống xử lý nhiều async transactions qua Message Queue
  • Cần tối ưu latency, detect performance bottlenecks
  • Cần debug cross-service issues trên Production
No
Not Recommended When
  • Ứng dụng Monolith đơn giản (chỉ cần centralized logs)
  • Hạ tầng giới hạn tài nguyên lưu trữ (trace logs dung lượng lớn)
  • Môi trường Local/Dev (không cần thiết)
  • Thiếu security mechanisms cho Trace Dashboard
