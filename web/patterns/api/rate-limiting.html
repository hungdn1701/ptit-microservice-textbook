Act 01

The Problem

Khi expose public APIs, nếu không kiểm soát tần suất request, hệ thống sẽ dễ overload do lượng truy cập đột biến (cả vô ý lẫn cố tình DDoS).

Exhaustion

Cạn kiệt tài nguyên (Resource Exhaustion)

Spam requests (ví dụ: data scraping, retry loops) chiếm dụng hoàn toàn thread pool và CPU. Gateway bị block, không thể route requests hợp lệ khác.

Brute-Force

Tấn công Brute-Force & Credential Stuffing

Attacker dùng botnet để dò mật khẩu liên tục qua Auth API. Nếu không có Rate Limiting, hacker có thể dò ra tài khoản và đồng thời làm sập Auth Service.

2
Act 02

The Pattern

Đặt một Filter tại API Gateway để đếm số lượng requests từ Client (theo IP, API Key, User ID). Nếu vượt ngưỡng, Gateway từ chối xử lý và trả về lỗi 429 Too Many Requests kèm HTTP header Retry-After.

— Rate Limiting Pattern · API Gateway Architecture

Thuật toán **Token Bucket** là giải pháp phổ biến: một bucket có dung lượng tối đa (Burst Capacity) được nạp token tự động ở tốc độ cố định (Replenish Rate). Mỗi request đi qua tiêu tốn 1 token. Khi bucket rỗng, request bị block.

Thành phần 01

Key Resolver

Định danh Client để áp dụng rate limit. Thường resolve qua: Địa chỉ IP (public route), User ID (từ JWT), hoặc Client/App ID (B2B API).

Thành phần 02

Distributed State với Redis

Lưu trữ state của token bucket. Sử dụng Redis (thông qua atomic Lua script) đảm bảo giới hạn chính xác khi scale Gateway ra nhiều instances (Distributed Rate Limiting).

Thành phần 03

HTTP 429 Handler

Trả về mã 429 và inject headers X-RateLimit-Remaining, X-RateLimit-Reset để chỉ dẫn Client thực hiện backoff.

Act 03

How It Works

Nhấp liên tục **Gửi Request** để tiêu tốn token. Quan sát quá trình Replenish và cách Gateway trả về 429 khi bucket rỗng.

Gateway RateLimiter Config
Tốc độ nạp (Replenish Rate) 2 tokens / giây
Dung lượng xô (Burst Capacity) 10 tokens
Số token hiện tại 10

Act 04 — Case Study

KBM: Apply It

Cấu hình Rate Limiting chi tiết tại kbm-gateway cho từng API route riêng biệt để tối ưu tài nguyên.

Cấu hình chi tiết các Endpoint KBM

Quyết định cấu hình xô token dựa trên độ nhạy cảm của API
API Routes Key Resolver Replenish Rate Burst Capacity Mục đích bảo vệ
/api/v1/auth/login Client IP Address 1 token / 3 giây 5 tokens CRITICAL: Ngăn chặn Brute-force, Credential Stuffing.
/api/v1/assignments/*/submit Student ID (JWT) 1 token / 5 giây 3 tokens HIGH: Ngăn spam submissions, tránh quá tải Judge engine.
/api/v1/courses/** (Queries) Student ID (JWT) 10 tokens / giây 20 tokens MED: Đảm bảo UX mượt mà, giới hạn spam API.
/static/** (Assets) Không áp dụng ∞ ∞ LOW: Static assets đã cache qua CDN/Nginx, không cần filter.

Lộ trình triển khai Rate Limiting

Tiến trình triển khai an toàn từ Dev đến Production
Phase 1

Setup Distributed Redis Cache

Thiết lập Redis cluster. Cấu hình Spring Cloud Gateway dùng RedisRateLimiter. Implement IpKeyResolver lấy IP Client thật (X-Forwarded-For).

Phase 2

Configure Route YAML & Headers

Khai báo RequestRateLimiter filter theo từng route. Cấu hình custom headers báo hiệu Rate Limit cho client-side.

Phase 3

Custom 429 Response & UI

Format lại JSON error message chuẩn xác cho mã 429. Frontend bắt lỗi và hiển thị UI Countdown chờ retry.

Phase 4

Observability & Alerting

Export metrics sang Prometheus. Cảnh báo qua Grafana nếu lỗi 429 spike (phát hiện DDoS/Brute-force) để tự động block IP qua Cloudflare.

Khi nào dùng — Khi nào không

✓
Nên dùng Rate Limiting khi
  • Public APIs expose cho bên thứ 3, Mobile/Web Client.
  • Compute-heavy endpoints (Báo cáo, Fuzzy Search, AI).
  • Auth APIs, OTP generation để chống spam.
  • Bảo vệ Database connection pool khỏi cạn kiệt.
✗
Không nên dùng khi
  • Internal service-to-service calls qua Private Network.
  • Static Assets (CSS, JS, Image) được phục vụ qua CDN.
  • Real-time streaming (WebSockets) không giới hạn bandwidth.
  • Chưa có Key Resolver đáng tin cậy (VD: vướng NAT IP chung).
