Act 01

The Problem

Trong hệ phân tán, mạng không đáng tin cậy. Khi client gửi yêu cầu thanh toán nhưng không nhận được phản hồi (timeout), nó buộc phải retry. Nếu server không nhận ra request trùng lặp, sinh viên có thể bị trừ tiền học phí 2 lần.

❌ Không có Idempotency Key
1. Client gửi POST /pay — 500.000đ
2. Server xử lý thành công, trừ tiền ✓
3. Response bị mất do network timeout ⚡
4. Client retry — gửi lại POST /pay
5. Server xử lý lại → trừ tiền lần 2! 💀
✓ Có Idempotency Key
1. Client gửi POST /pay + Idempotency-Key: abc
2. Server xử lý, lưu kết quả kèm key ✓
3. Response bị mất do network timeout ⚡
4. Client retry — gửi lại cùng key abc
5. Server nhận ra key trùng → trả cached response ✓
Double Charge

Trừ tiền trùng lặp

Payment API xử lý cùng 1 giao dịch 2 lần. Sinh viên bị trừ học phí 1.000.000đ thay vì 500.000đ. Hoàn tiền thủ công mất 3-5 ngày.

Ghost Orders

Đơn hàng ma (Ghost Orders)

Retry tạo ra nhiều bản ghi đăng ký môn học trùng nhau trong database. Phòng Đào tạo thấy dữ liệu sai, sinh viên bị lộn lớp.

Act 02

The Pattern

Client đính kèm một Idempotency Key (UUID duy nhất) vào mỗi yêu cầu ghi (POST/PUT). Server lưu key + kết quả vào bảng processed_requests. Nếu nhận lại request với key đã tồn tại, server trả về kết quả đã lưu thay vì xử lý lại.

— Idempotent Consumer Pattern · Microservices Patterns (Richardson, 2018)
Thành phần 01

Idempotency Key

UUID do client sinh ra, gắn trong HTTP header Idempotency-Key. Mỗi thao tác nghiệp vụ (thanh toán, đăng ký) có 1 key riêng. Client giữ nguyên key khi retry.

Thành phần 02

Processed Request Store

Bảng processed_requests trong DB (hoặc Redis) lưu {key, response, status, created_at}. Dùng UNIQUE constraint trên key để ngăn race condition.

Thành phần 03

Dedup Filter

Middleware kiểm tra key trước khi xử lý: nếu key tồn tại → trả cached response (HTTP 200 + body cũ). Nếu chưa → xử lý bình thường và lưu kết quả.

Act 04 — Case Study

KBM: Apply It

Hệ thống KBM triển khai Idempotency ở 2 tầng: REST API (Idempotency-Key header) cho các thao tác ghi từ Mobile/Web, và Kafka Consumer (processed-message table) để chống duplicate event.

Các endpoint áp dụng Idempotency Key

Chỉ áp dụng cho thao tác ghi (non-idempotent methods)
API Endpoint Method Idempotency Key Lý do
/api/v1/payments POST ✅ Bắt buộc CRITICAL: Thanh toán học phí — không được trừ tiền 2 lần.
/api/v1/enrollments POST ✅ Bắt buộc HIGH: Đăng ký môn học — không được tạo enrollment trùng.
/api/v1/assignments/*/submit POST ✅ Bắt buộc MED: Nộp bài — không được nộp trùng cùng 1 lần submit.
/api/v1/courses GET Không cần SAFE: GET là idempotent theo HTTP spec.

Lộ trình triển khai Idempotency

Từ prototype đến production-ready
Phase 1

Idempotency Key Filter

Tạo Spring @IdempotencyKey annotation + IdempotencyFilter. Lưu key vào bảng processed_requests với UNIQUE constraint. Trả cached response nếu key đã tồn tại.

Phase 2

Kafka Consumer Dedup

Bộ tiêu thụ Kafka kiểm tra message_id trong bảng processed_messages trước khi xử lý. INSERT ... ON CONFLICT DO NOTHING đảm bảo exactly-once semantics.

Phase 3

TTL & Cleanup

Thiết lập TTL 7 ngày cho bảng processed_requests (dùng scheduled job hoặc Postgres partitioning). Ngăn bảng phình vô hạn.

Phase 4

Client-side SDK

Mobile/Web SDK tự động sinh Idempotency-Key: UUID cho mỗi mutation request. Lưu key vào localStorage để giữ nguyên khi retry.

Khi nào dùng — Khi nào không

✓
Nên dùng Idempotency Key khi
  • API thanh toán, chuyển tiền, đặt hàng — hậu quả lớn nếu duplicate.
  • Kafka/RabbitMQ consumers — at-least-once delivery cần dedup.
  • Mobile app với mạng không ổn định (3G, Wi-Fi yếu).
  • Webhook receivers — provider có thể gửi lại cùng 1 event.
✗
Không cần khi
  • GET requests — đã idempotent theo HTTP spec.
  • PUT/DELETE requests — tự nhiên idempotent (set state, not mutate).
  • Internal sync calls với gRPC + deadline (retry ngắn, low risk).
  • Read-heavy APIs không có side-effect (dashboard, query).
