Act 01

Sự trùng lặp mã nguồn & Lỗ hổng bảo mật

Khi không có một API Gateway đứng chặn ở cổng ngõ hệ thống, mỗi microservice nội bộ phải tự chịu trách nhiệm xử lý các tác vụ biên hạ tầng như cấu hình CORS, giải mã JWT, Rate Limiting và định tuyến đường dẫn. Điều này mang lại nhiều vấn đề nghiêm trọng cho phát triển và vận hành.

⚙️

Trùng lặp logic & Khó bảo trì (Boilerplate)

Cả 5 dịch vụ nghiệp vụ đều phải cài đặt thư viện và viết filter giải mã JWT giống hệt nhau. Khi cần nâng cấp thuật toán mã hóa (ví dụ: chuyển từ HS256 sang RS256) hoặc đổi Secret Key, đội phát triển phải cập nhật cấu hình và redeploy tất cả các dịch vụ.

🔓

Rủi ro bảo mật & Inconsistent CORS

Mỗi microservice tự cấu hình chính sách CORS riêng biệt. Chỉ cần một lập trình viên cấu hình nhầm thành Allow-Origin: * ở một service phụ, hacker có thể khai thác. Hơn nữa, trình duyệt của người dùng liên tục bị block preflight request do cấu hình CORS lệch nhau giữa các service.

🚨

KBLab Incident — Lỗi lộ Secret Key JWT và sập đồng loạt do cấu hình sai

Trong thiết kế ban đầu của KBLab, cả kblab-app, kblab-assignment và kblab-judge đều tự đọc file cấu hình chứa JWT secret key để xác thực. Khi khóa bí mật bị rò rỉ, quản trị viên thay đổi khóa trên máy chủ cấu hình. Do kblab-judge gặp sự cố khởi động lại chậm, nó vẫn giữ khóa cũ khiến toàn bộ sinh viên chấm bài thi bị từ chối kết quả chấm điểm do chữ ký token không khớp, trong khi vẫn đăng nhập và xem đề thi bình thường.

Act 02

API Gateway Routing Pipeline

Thiết lập một API Gateway làm seam (đường nối) duy nhất đón nhận mọi request từ Client. Chạy một chuỗi các bộ lọc (Filter Chain) tập trung để giải quyết CORS, xác thực JWT, và rate limit trước khi định tuyến. Sau khi xác thực thành công, Gateway giải mã token, gắn thông tin danh tính (như User ID) vào HTTP Header và forward request sạch đến các service nội bộ.

— API Gateway Routing · Microservice Patterns (Chris Richardson)

Mẫu thiết kế này đưa các dịch vụ nội bộ về vùng an toàn (Private Network), giúp chúng hoàn toàn stateless và tập trung 100% vào logic nghiệp vụ thay vì lo lắng về hạ tầng bảo mật.

Thành phần 01

Routing Predicates

Các điều kiện khớp mẫu đường dẫn URL (ví dụ: match /api/v1/courses/**) để xác định request sẽ được chuyển tiếp tới dịch vụ nội bộ nào thông qua Service Discovery.

Thành phần 02

Pre/Post Filter Chain

Các filter chạy trước (Pre) và sau (Post) khi định tuyến. Pre-filters thực hiện giải mã token, ghi log, rate limit. Post-filters bổ sung các header phản hồi, đo lường thời gian phản hồi hoặc nén dữ liệu.

Thành phần 03

Gateway-to-Service Trust

Sau khi giải mã JWT thành công, Gateway chèn header X-User-Id và X-User-Roles vào request. Các microservice downstream chỉ cần đọc các header này và tuyệt đối tin tưởng Gateway (không cần giải mã lại JWT).

Lộ trình triển khai Gateway

Tiến trình triển khai định tuyến an toàn
Phase 1 · Tuần 1

Xây dựng Gateway Core & Cấu hình Routes YAML

Khởi tạo project Spring Cloud Gateway (sử dụng WebFlux reactive engine non-blocking). Khai báo các Route định tuyến sang dịch vụ nội bộ thông qua Registry Eureka service ID.

Dự kiến: 1 dev × 3 ngày
Phase 2 · Tuần 2

Viết Custom Global JWT Filter & Header Injection

Implement bộ lọc JwtRequestFilter. Giải mã JWT chữ ký RSA công khai, trích xuất userId và roles, chuyển chúng thành HTTP Headers để chuyển tiếp an toàn xuống downstream.

✓ Loại bỏ hoàn toàn logic JWT ở các dịch vụ con
Phase 3 · Tuần 3

Cấu hình CORS & Cảnh báo an toàn an ninh

Cài đặt chính sách CORS toàn cục tại Gateway, loại bỏ cấu hình CORS ở các service con. Thêm các HTTP Security Headers bảo vệ ứng dụng (X-Content-Type-Options, X-Frame-Options, Content-Security-Policy).

Dự kiến: 1 dev × 2 ngày
Phase 4 · Tuần 4

Đồng bộ bảo mật mạng nội bộ (mTLS / Network Policy)

Chỉ cho phép các dịch vụ con nhận traffic xuất phát từ Gateway. Thiết lập Kubernetes NetworkPolicy hoặc cấu hình Security Group để chặn tất cả kết nối trực tiếp từ Internet vào các service nội bộ.

✓ Hoàn tất thiết lập mạng lưới Private đáng tin cậy

Khi nào dùng — Khi nào không

✅
Nên dùng API Gateway khi
  • Kiến trúc có trên 3 microservices nghiệp vụ độc lập
  • Hệ thống phục vụ đa dạng các client (Web, Mobile, Third-party)
  • Cần quản lý tập trung bảo mật, CORS, rate limiting, log truy cập
  • Cần che giấu cấu trúc mạng nội bộ để chống tấn công quét cổng ngõ
❌
Không nên dùng khi
  • Hệ thống chỉ gồm 1 monolith hoặc kiến trúc cực kỳ đơn giản (over-engineering)
  • Ứng dụng yêu cầu truyền dữ liệu file siêu lớn (Gateway có thể trở thành nút thắt cổ chai nghẽn mạng)
  • Yêu cầu độ trễ mạng cực thấp gần như bằng không (mỗi bước đi qua Gateway tăng thêm 1-3ms latency)
  • Các microservices nghiệp vụ hoàn toàn độc lập và không dùng chung cơ chế định danh auth
