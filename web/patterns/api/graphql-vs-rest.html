Act 01

Lỗi N+1 Queries và dư thừa dữ liệu (Over-fetching)

Khi xây dựng Client Frontend (như trang Web hoặc Mobile), giao diện thường hiển thị dữ liệu dạng cây thứ bậc (ví dụ: hiển thị danh sách các bài tập lớn, và đối với mỗi bài tập, hiển thị danh sách các lượt nộp bài của sinh viên). Sử dụng các endpoint REST API truyền thống sẽ mang lại nhiều bất cập lớn.

🐢

Thắt cổ chai N+1 mạng (N+1 Network Roundtrips)

Ứng dụng Client phải gọi 1 request để lấy danh sách N bài tập lớn. Sau đó, nó phải thực hiện thêm N request độc lập tiếp theo để lấy thông tin các lượt nộp bài cho từng bài tập đó. Tổng cộng hệ thống tiêu tốn N+1 network requests, gây lag giao diện khi mạng yếu (3G/4G).

📦

Tải thừa dữ liệu (Over-fetching)

Các REST endpoint thường trả về toàn bộ trường dữ liệu của thực thể. Frontend có thể chỉ cần hiển thị tiêu đề và điểm số, nhưng API trả về cả nội dung mã nguồn, log chấm bài, email người dùng... Điều này làm phình kích thước payload, lãng phí băng thông mạng.

🚨

KBLab Incident — 21 request nghẽn mạng do nạp dashboard thi trắc nghiệm

Tại trang chủ của sinh viên, frontend hiển thị danh sách 20 bài kiểm tra và trạng thái bài làm tương ứng. Do sử dụng REST API, frontend gửi 1 cuộc gọi tới /api/assignments, và 20 cuộc gọi đồng thời tới /api/assignments/{id}/submissions. Trên mạng di động, trang chủ mất 4 giây để load xong, và hệ thống Gateway ghi nhận quá tải lượng request đột biến dù sinh viên mới chỉ đăng nhập.

Act 02

GraphQL & DataLoader Pattern

GraphQL: Cung cấp một cổng truy vấn duy nhất. Client gửi một truy vấn (Query DSL) mô tả chính xác cấu trúc dữ liệu và các trường cần lấy. Server trả về đúng những gì client yêu cầu trong 1 request duy nhất.
DataLoader: Cơ chế batching (gom nhóm) và caching các truy vấn database ở tầng server. Tránh việc dịch chuyển lỗi N+1 từ mạng (Network) xuống thành N+1 truy vấn database (SQL query).

— GraphQL Architecture · Facebook (2015)

Bằng cách sử dụng **DataLoader**, các truy vấn database đơn lẻ trong Resolver được gom nhóm thành một câu lệnh SQL IN (?,?,?...) duy nhất để tối ưu hóa hiệu năng Database.

Thành phần 01

Single Gateway Endpoint

Client chỉ kết nối tới một endpoint duy nhất (thường là POST /graphql) và gửi query dạng JSON chỉ rõ các trường dữ liệu cần thiết.

Thành phần 02

Field Resolvers

Các hàm xử lý tương ứng trên server để lấy dữ liệu cho từng trường cụ thể trong Schema. Cho phép kết hợp dữ liệu từ nhiều nguồn khác nhau (Database, Cache, REST API khác).

Thành phần 03

DataLoader Batching

Hệ thống hoãn thực thi các câu query DB riêng lẻ, chờ gom tất cả các khóa (IDs) của các Resolver cha, sau đó chạy 1 câu query gộp. Giải quyết triệt để lỗi N+1 DB.

Act 04

Giải pháp tối ưu hóa API KBLab

KBLab áp dụng GraphQL BFF (Backend-for-Frontend) làm tầng trung gian giúp tổng hợp dữ liệu mượt mà cho giao diện Web/Mobile.

Phân tích chênh lệch giải pháp API

Tiêu chí REST API truyền thống GraphQL Gateway Quyết định áp dụng tại KBLab
Số cuộc gọi mạng (Dashboard) 21 requests (N+1 bottleneck) 1 request duy nhất Áp dụng cho trang chủ Dashboard chứa dữ liệu tổng hợp từ nhiều nguồn.
Tự động chọn trường (Field Selection) Không (Luôn trả payload đầy đủ cố định). Tự chọn trường linh hoạt theo query. Tiết kiệm tới 65% băng thông payload cho Mobile app chạy 4G.
Quản trị bảo mật (DDoS) Đơn giản (Chỉ cần giới hạn rate limit URL). Phức tạp (Nguy cơ DDoS qua query lồng nhau). Phải cài đặt bộ lọc độ sâu Query (Query Depth Limiter) tối đa 5 cấp.

Lộ trình triển khai GraphQL

Các bước tích hợp an toàn hệ thống truy vấn
Phase 1 · Tuần 1

Xác định Schema Definitions & Queries

Thiết lập dự án GraphQL Spring Boot. Định nghĩa tệp schema.graphqls mô tả các kiểu dữ liệu: Assignment, Submission, User và các queries tương ứng.

Dự kiến: 1 dev × 3 ngày
Phase 2 · Tuần 2

Cài đặt Resolver & Tích hợp Spring Data

Viết các class Controller Resolver để liên kết dữ liệu từ các Repository hiện có. Test truy vấn cơ bản qua công cụ GraphiQL playground.

✓ Hoàn thành các query lấy dữ liệu cơ bản
Phase 3 · Tuần 3

Tối ưu hóa Database với DataLoader

Đăng ký các DataLoader trong cấu hình. Thay thế logic gọi DB đơn lẻ bằng cơ chế nạp batching (sử dụng IN (?,?,...) queries) để giải quyết lỗi N+1 DB.

Dự kiến: 1 dev × 4 ngày
Phase 4 · Tuần 4

Thiết lập giới hạn độ phức tạp câu query (Security Guard)

Ngăn chặn hacker khai thác query lồng nhau vô hạn để làm treo server (ví dụ: query gọi đệ quy A->B->A->B...). Cài đặt MaxQueryDepthInstrumentation giới hạn độ sâu tối đa là 5.

✓ Hệ thống API GraphQL an toàn hoạt động 100%

Khi nào dùng — Khi nào không

✅
Nên dùng GraphQL khi
  • Cần xây dựng tầng Backend-for-Frontend (BFF) cho đa dạng thiết bị (Web, Mobile, Smartwatch)
  • Hệ thống có nhiều mối quan hệ dữ liệu lồng nhau phức tạp cần hiển thị đồng thời
  • Băng thông mạng di động là cực kỳ quan trọng, cần tối giản hóa payload trả về
  • Cần hỗ trợ cập nhật giao diện linh hoạt mà không cần đổi version API liên tục
❌
Không nên dùng khi
  • Kiến trúc API cực kỳ đơn giản, chỉ cần đọc/ghi phẳng (REST đơn giản nhanh hơn)
  • Hệ thống thực hiện truyền tải các file nhị phân (Upload/Download File lớn)
  • Cần sử dụng HTTP Caching ở tầng proxy/CDN (GraphQL dùng POST nên khó cache Web mặc định)
  • Chưa có giải pháp bảo vệ độ sâu câu query (Rủi ro DDoS cao)
