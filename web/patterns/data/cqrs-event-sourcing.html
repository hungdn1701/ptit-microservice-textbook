Act 01

The Problem

Trong hệ thống CRUD truyền thống, Read và Write dùng chung database schema. Khi lưu lượng đọc tăng vọt, các truy vấn phức tạp (nhiều JOIN) sẽ lock table, gây nghẽn luồng ghi.

[Low]

Table Lock & Tăng Latency Write

Khi thực thi query phức tạp, database áp dụng shared lock trên các row. Điều này block INSERT hoặc UPDATE, làm tăng latency của write API.

[Error]

Mất audit trail

Hệ thống CRUD chỉ lưu current state. Khi update, trạng thái cũ bị overwrite. Việc truy vết lịch sử nghiệp vụ (audit trail) rất phức tạp và thiếu tin cậy.

2
Act 02

The Pattern

CQRS: Tách hệ thống thành hai luồng độc lập: Command side (chỉ write, dùng DB tối ưu ghi) và Query side (chỉ read, dùng DB tối ưu đọc như Materialized View).
Event Sourcing: Trạng thái thực thể là một chuỗi immutable events trong Event Store. Current state được tái tạo bằng cách replay các events này.

— Greg Young & Martin Fowler · Enterprise Integration Patterns

Kiến trúc này cho phép scale độc lập luồng read và write, đồng thời cung cấp audit trail tin cậy tuyệt đối.

Thành phần 01

Command Side (Write)

Nhận Command từ client, validate nghiệp vụ và append events vào Event Store. Đây là Source of Truth duy nhất của hệ thống.

Thành phần 02

Event Projector

Worker chạy ngầm lắng nghe Event Store (qua Kafka). Khi có event mới, Projector biến đổi và cập nhật data vào Read Database (Redis/Elasticsearch).

Thành phần 03

Query Side (Read)

Xử lý Query từ client. Đọc trực tiếp từ Read Database (dữ liệu đã denormalize, không JOIN, low latency).

Act 04 — Case Study

KBM: Apply It

KBM áp dụng CQRS cho module thi trực tuyến nhằm giảm tải cho master database.

Phân tích chênh lệch và Quyết định kỹ thuật

Bảng so sánh mô hình CRUD truyền thống và mô hình CQRS/ES
Tiêu chí Monolith CRUD ban đầu Kiến trúc CQRS + ES đề xuất Lý do kỹ thuật (Trade-off)
Độ trễ truy vấn (Read Latency) Cao (1-3s) do SQL JOIN phức tạp. Thấp (< 10ms) nhờ đọc trực tiếp từ Redis. Read model được denormalize sẵn, tối ưu hóa cho tốc độ đọc.
Khả năng ghi (Write Throughput) Bị block chéo do lock table từ luồng read. Độc lập, append event trực tiếp vào log. Không bị ảnh hưởng bởi tải đọc của client.
Tính nhất quán (Consistency) Strong Consistency. Eventual Consistency qua Kafka. Bảng xếp hạng chấp nhận trễ 1-2 giây để đổi lấy khả năng chịu tải.
Độ phức tạp (Complexity) Thấp, chỉ là CRUD cơ bản. Cao, cần xử lý async, duplicate event. Đội ngũ vận hành cần có kinh nghiệm về Kafka và Redis.

Lộ trình triển khai CQRS & Event Sourcing

Các bước thực thi triển khai nâng cấp hạ tầng dữ liệu
Phase 1 · Tuần 1

Tách Command/Query tại tầng Application

Dùng Mediator pattern (Spring Event). Tách service thành CreateSubmissionCommandHandler và GetLeaderboardQueryHandler.

Dự kiến: 2 devs × 4 ngày
Phase 2 · Tuần 2

Setup Event Store

Cấu hình bảng event_store trên PostgreSQL. Chuyển đổi dữ liệu nộp bài thành chuỗi event: SubmissionCreated, TestCasesExecuted, ScoreCalculated.

✓ Lưu lịch sử bằng append-only log
Phase 3 · Tuần 3

Build Projector cập nhật Redis Read Model

Triển khai worker consume Kafka. Xử lý event và cập nhật trực tiếp vào Redis Sorted Set (ZSET) để query bảng xếp hạng real-time.

Dự kiến: 1 dev × 1 tuần
Phase 4 · Tuần 4

Cài đặt Snapshotting tối ưu performance

Khi số event của Aggregate vượt 10,000, quá trình replay sẽ chậm. Áp dụng snapshotting định kỳ mỗi 1,000 events để giảm thời gian load.

✓ Tối ưu thời gian load Aggregate

Khi nào dùng — Khi nào không

[OK]
Nên dùng CQRS & Event Sourcing khi
  • Read throughput lớn hơn write gấp nhiều lần (Leaderboard, News feed).
  • Yêu cầu audit trail nghiêm ngặt, bất biến (Wallet, Banking).
  • Cần tổng hợp data từ nhiều nguồn cho các read model khác nhau.
  • Cần khả năng rollback aggregate state về thời điểm bất kỳ (Time travel).
[Error]
Không nên dùng khi
  • CRUD đơn giản, throughput thấp (Over-engineering).
  • Yêu cầu strong consistency ngay sau khi write.
  • Thiếu kinh nghiệm vận hành Message Broker và Eventual Consistency.
  • Xây dựng MVP, cần time-to-market nhanh.
