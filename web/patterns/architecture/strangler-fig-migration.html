Act 01

The Problem

Hệ thống của bạn đang scale. Team đang phình to. Deploy ngày càng chậm. Bạn biết mình cần microservices — nhưng codebase đang chạy production 3 năm và không ai dám nói "viết lại từ đầu."

🔗

Tight Coupling — Thay một thứ, vỡ mọi thứ

Module Auth, Course, và Judge share cùng database. Một schema migration của Auth lock table của Course. Không ai dám touch production trước deadline thi.

🐢

Deploy toàn bộ — All or nothing

Team A fix bug trong Payment. Phải đợi team B finish feature trong Notification. Mỗi deploy là một sự kiện toàn team, kéo dài 4 giờ, ai cũng lo lắng.

📈

Không scale được phần muốn

Mùa thi, Judge cần 10× CPU. Nhưng Judge nằm trong monolith — scale monolith = scale tất cả, lãng phí 10× chi phí, làm chậm các module khác.

💀

Big Bang Rewrite — Cái bẫy cổ điển

Nhiều team đã thử: "viết lại sạch trong 6 tháng." Sau 18 tháng, hệ thống mới thiếu 30% tính năng cũ. Project bị huỷ. Monolith vẫn đó, với thêm technical debt.

Act 02

The Pattern

Tách dần các chức năng ra khỏi monolith — từng phần, từng sprint — trong khi monolith vẫn chạy và serve traffic. Sử dụng API Gateway làm seam: route traffic sang service mới khi ready, fallback về monolith khi cần. Không có "ngày switch" — chỉ có quá trình thay thế liên tục cho đến khi monolith teo dần và biến mất.

— Strangler Fig Application · Martin Fowler (2004) · [W2]

Tên gọi lấy cảm hứng từ cây đa bóp nghẹt (strangler fig) — loại cây bám vào cây chủ, dần thay thế cho đến khi cây chủ biến mất, trong khi cây đa vẫn đứng vững và phát triển.

Thành phần 01

API Gateway / Seam

Điểm đơn để redirect traffic. Client không biết phần nào đang serve từ monolith, phần nào từ service mới.

Thành phần 02

New Service

Build song song, deploy độc lập, database riêng. Chỉ nhận traffic khi đã verified bằng Canary hoặc Parallel Run.

Thành phần 03

Monolith (Legacy)

Vẫn chạy và serve phần chưa tách. Mỗi feature được extract, monolith shrink. Cuối cùng có thể retire hoặc giữ làm fallback.

Act 04 — Case Study

KBLab: Apply It

KBLab LMS là hệ thống chấm điểm SQL đang production với sinh viên nộp bài mỗi ngày. Không thể Big Bang rewrite. Đây là migration roadmap thực tế dùng Strangler Fig theo thứ tự ưu tiên.

Migration Timeline

Thứ tự quan trọng hơn tốc độ — Quick Wins trước, High-Risk thay đổi sau

Tuần 1–2 · Phase 0

Thêm API Gateway — transparent proxy, zero downtime

Deploy Spring Cloud Gateway phía trước monolith. Verify 100% requests đi qua Gateway mà không tăng latency > 5ms. Fully reversible.

Effort: 1 dev × 2 ngày
Tuần 3–4 · Phase 1

Extract Auth → Keycloak (canary 10% → 100%)

Deploy Keycloak, migrate user credentials. Gateway route /auth/* sang Keycloak với canary 10%. Monitor error rate 48h → switch 100% → delete Auth module khỏi monolith.

✓ Independent deploy achieved
Tháng 2–3 · Phase 2

Schema Separation — Core ↔ Assignment DB

Tách shared PostgreSQL thành 2 schemas. Thêm Outbox Pattern cho reliable events. Database views làm bridge trong giai đoạn chuyển tiếp — không downtime.

Effort: 2 devs × 3 tuần
Tháng 4–6 · Phase 3

Judge Service độc lập — Kafka event-based

Judge workers nhận submission qua Kafka topic. Scale Judge × 10 trong mùa thi mà không ảnh hưởng Core. Parallel Run 2 tuần trước khi switch toàn bộ traffic.

✓ Independent scaling achieved

Khi nào dùng — Khi nào không

✅
Phù hợp khi
  • Hệ thống đang production, không thể downtime
  • Cần migrate dần dần, mỗi bước phải reversible
  • Có bounded context rõ ràng (DDD, Event Storming)
  • Team ≥ 3 người, có thể handle parallel work
  • API Gateway đã có hoặc dễ thêm vào
❌
Không phù hợp khi
  • Hệ thống quá nhỏ — overhead vận hành không đáng
  • Monolith well-structured, chỉ cần modular hóa nội bộ
  • Không có observability — không biết migration đúng không
  • Database coupling quá sâu (stored procedures, triggers)
  • Team chưa quen với distributed systems và async patterns
