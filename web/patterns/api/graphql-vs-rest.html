1
Act 01

The Problem

Khi frontend (web, mobile) cần dữ liệu phân cấp — ví dụ danh sách câu hỏi kèm điểm các bài nộp của từng câu — REST truyền thống bộc lộ ba hạn chế: over-fetching, under-fetching và nhiều vòng gọi mạng (§3.7).

N+1

N+1 lượt gọi mạng

Client gọi 1 request lấy N câu hỏi, rồi thêm N request để lấy bài nộp của từng câu. Tổng cộng N+1 lượt gọi mạng — độ trễ cộng dồn, đặc biệt tốn kém trên mobile (§3.7).

Over-fetch

Over-fetching

Endpoint REST trả cấu trúc cố định: GET /questions/1 trả 20 trường trong khi mobile chỉ cần title và difficulty — payload phình, tốn băng thông (§3.7).

2
Act 02

The Pattern

GraphQL: Cung cấp single endpoint. Client gửi Query DSL xác định chính xác cấu trúc và fields cần thiết. Server trả về đúng payload yêu cầu trong 1 request.
DataLoader: Cơ chế batching và caching ở server. Ngăn chặn việc đẩy bài toán N+1 từ network xuống database (SQL N+1).

— GraphQL Architecture · Facebook (2015)

Sử dụng DataLoader, các DB query rời rạc trong Resolver được batching thành 1 câu SQL IN (?,?,...) duy nhất để tối ưu performance.

Thành phần 01

Single Endpoint

Client gọi POST /graphql với Query JSON định nghĩa chính xác data schema.

Thành phần 02

Field Resolvers

Hàm xử lý fetch dữ liệu cho từng field trong Schema, cho phép tổng hợp data từ nhiều nguồn (DB, Cache, REST APIs).

Thành phần 03

DataLoader Batching

Hoãn thực thi các câu SQL đơn lẻ, gom nhóm IDs từ các Parent Resolvers để chạy 1 batch query, loại bỏ N+1 Database problem.

How It Works

Act 04 — Case Study

KBM: Apply It

KBM hiện dùng REST cho LMS core: đơn giản, dễ debug, có OpenAPI. Theo §3.7, GraphQL chỉ phát huy giá trị nếu KBM bổ sung (1) mobile app, (2) dashboard giảng viên tổng hợp dữ liệu nhiều service, (3) API cho bên thứ ba. GraphQL không thay REST: REST giữa các service, GraphQL ở lớp BFF.

Khi nào chọn REST, khi nào chọn GraphQL

Theo bảng lựa chọn ở §3.7, kèm áp dụng vào KBM

Không phải việc KBM đã làm — là trình tự hợp lý theo §3.7

Giai đoạn 1

Viết schema trước (schema-first)

Định nghĩa type Question, Submission, Query như ví dụ §3.7. Schema vừa là tài liệu, vừa là hợp đồng giữa team frontend và backend.

Kết quả: schema được review như OpenAPI spec
Giai đoạn 2

Resolver ở lớp BFF gọi REST sẵn có

GraphQL server đứng trước kbm-core và kbm-academic; resolver gọi REST API hiện tại — không đổi giao tiếp giữa các service.

REST giữa service, GraphQL cho client
Giai đoạn 3

DataLoader chặn N+1

Gom lời gọi submissions theo lô: WHERE question_id IN (…). Đây là điều kiện bắt buộc — GraphQL để client quyết định truy vấn nên server phải tự xử lý N+1.

✓ 1 request, 2 truy vấn
Giai đoạn 4

Giới hạn độ sâu và độ phức tạp query

Chặn truy vấn lồng nhau vô hạn trước khi mở cho client ngoài; kết hợp rate limiting ở Gateway (Ch.8).

✓ An toàn trước truy vấn độc hại

Khi nào dùng — Khi nào không

✓
Nên dùng GraphQL khi
  • Xây dựng BFF phục vụ nhiều loại client (Web, mobile).
  • Mô hình dữ liệu phân cấp sâu, nhiều quan hệ.
  • Ứng dụng mobile cần payload nhỏ trên mạng chậm.
  • Giao diện đổi nhanh, không muốn ra version API liên tục.
✗
Không nên dùng khi
  • CRUD đơn giản, dữ liệu phẳng (REST là đủ).
  • Tải lên/tải xuống file nhị phân lớn.
  • Cần cache HTTP/CDN (GraphQL dùng POST, khó cache).
  • API công khai chưa kiểm soát được độ phức tạp query (nguy cơ DDoS).
