Act 01

The Problem

Khi nhiều team cùng build một hệ thống lớn, mỗi team có model riêng cho các khái niệm chung — và không ai biết ai đang dùng gì của ai.

🗺️

Ambiguous Ubiquitous Language

"User" trong team Auth là người đăng nhập. "User" trong team Core là learner có enrollment. Cùng từ, khác model — silent bugs khi integrate.

🔀

Implicit Integration — Không ai biết dependency

Assignment Service gọi Core Service API mà không document rõ. Team Core refactor field userId → learnerId làm Assignment crash production.

🌐

Shared Database Anti-pattern

Core và Assignment share cùng DB schema. Schema changes của team này break queries của team kia. Không ai dám refactor — "fear of breaking others."

📜

Undocumented Team Relationships

Ai là upstream? Ai là downstream? Khi Core thay đổi API, Assignment có biết không? Không có "bản đồ" → integration chaos và blame game khi có lỗi.

Act 02

The Pattern

Context Map là bản đồ toàn cục của hệ thống — hiển thị tất cả Bounded Contexts, ranh giới giữa chúng, và mối quan hệ tích hợp (upstream/downstream, shared kernel, anti-corruption layer...). Đây là tài liệu sống, không phải sơ đồ kiến trúc tĩnh.

— Eric Evans, Domain-Driven Design [6, Ch.14] · 2003

Mỗi mối quan hệ giữa hai Bounded Contexts được gọi là một Integration Pattern. Một số patterns phổ biến:

U — Upstream (nhà cung cấp) D — Downstream (phụ thuộc) SK — Shared Kernel CF — Conformist ACL — Anti-Corruption Layer OHS — Open Host Service
Upstream (U)

Nhà cung cấp

Định nghĩa API/model. Thay đổi phía Upstream ảnh hưởng Downstream. VD: Auth Service là Upstream của Core.

Downstream (D)

Người phụ thuộc

Phụ thuộc vào Upstream. Nếu Upstream thay đổi, Downstream phải adapt hoặc dùng ACL để tự bảo vệ.

ACL

Anti-Corruption Layer

Lớp dịch thuật ở phía Downstream — convert model của Upstream sang ngôn ngữ riêng, không để Upstream "ô nhiễm" domain model của mình.

Act 04 — Case Study

KBLab: Apply It

KBLab có 5 Bounded Contexts chính. Mapping rõ ràng mối quan hệ giúp team tránh integration accidents và plan API changes có trách nhiệm.

Context Relationship Map

Upstream/Downstream và Integration Pattern cho từng cặp

Assignment Judge Conformist + Event Judge API change → Assignment must update

Migration Timeline

Từ implicit coupling → explicit Context Map

Tuần 1 · Phase 0

Event Storming — vẽ bản đồ domain hiện tại

Workshop 2 ngày với tất cả team. Identify bounded contexts, aggregate, domain events. Output: draft Context Map trên whiteboard.

Effort: Toàn team × 2 ngày
Tuần 2 · Phase 1

Document mối quan hệ hiện tại — không thay đổi code

Vẽ chính thức Context Map. Identify upstream/downstream, shared kernels, implicit dependencies. Đây là bức tranh hiện tại — base line.

Output: context-map.md trong repo
Tháng 1 · Phase 2

Thêm Contract Tests cho các integration points HIGH risk

Auth → [Core, Assignment]: thêm Pact consumer-driven contract tests. Mỗi khi Auth thay đổi API, CI tự động verify tất cả consumers không bị break.

✓ Safe API evolution
Tháng 2+ · Phase 3

Anti-Corruption Layer cho Core → Assignment

Assignment Service tự build ACL layer để translate Core domain objects sang Assignment domain language. Core có thể refactor internal model mà không break Assignment.

✓ Team autonomy achieved

Khi nào dùng — Khi nào không

✅
Phù hợp khi
  • Nhiều team cùng build trên cùng hệ thống
  • Có nhiều domain model phức tạp, dễ nhầm lẫn
  • Đang lên kế hoạch migrate sang microservices
  • Cần identify integration risk trước khi refactor
❌
Không cần thiết khi
  • Hệ thống rất nhỏ, 1 team, 1 domain
  • Domain model đơn giản, không có ngôn ngữ mơ hồ
  • Prototype / MVP — context map sẽ thay đổi quá nhanh
