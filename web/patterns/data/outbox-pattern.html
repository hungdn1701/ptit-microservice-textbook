Act 01

The Problem

Khi một microservice cần thực hiện đồng thời hai thao tác: cập nhật Database và publish Event lên Message Broker (Kafka/RabbitMQ). Việc gọi tuần tự hai hệ thống phân tán không có distributed transaction sẽ gây ra rủi ro nghiêm trọng về tính nhất quán dữ liệu.

[Error]

Lỗi khi Publish Message

Ứng dụng commit Database thành công. Tuy nhiên, sau đó mạng chập chờn hoặc Broker sập, publish message failed. Do Database transaction đã commit nên không thể rollback. Hệ quả: Event bị mất vĩnh viễn, downstream service không nhận được thông báo.

[Ghost]

Phantom Event (Sự kiện ma)

Nếu đảo ngược: publish Event lên Broker trước, rồi mới lưu Database. Nếu Database gặp lỗi (vi phạm constraint) và bị rollback. Event đã đẩy lên Broker không thể thu hồi. Downstream service sẽ nhận và xử lý "Phantom Event", gây sai lệch trạng thái.

Act 02

The Pattern

Thay vì gửi Event thẳng lên Message Broker, ứng dụng insert Event vào một bảng OUTBOX cùng với thao tác lưu dữ liệu nghiệp vụ, gói gọn trong một Local ACID Transaction. Sau đó, một process chạy ngầm (Message Relay) sẽ đọc bảng Outbox và publish message lên Broker với cơ chế At-Least-Once Delivery.

— Transactional Outbox Pattern · Enterprise Integration Patterns

Sử dụng ACID transaction cục bộ của RDBMS để đảm bảo tính nguyên tử: hoặc cả thao tác nghiệp vụ và Event đều thành công, hoặc rollback cả hai.

Thành phần 01

Outbox Table

Bảng lưu trữ Event nằm trong cùng Database nghiệp vụ. Schema thường gồm: id, aggregate_type, aggregate_id, payload (JSON), và status (PENDING, SENT).

Thành phần 02

Local ACID Transaction

Service xử lý logic: lưu Entity và insert Event vào bảng Outbox trong cùng một transaction. Với Spring Boot, thao tác này được bọc bởi @Transactional.

Thành phần 03

Message Relay

Process chạy ngầm publish Event lên Broker. Hai mô hình phổ biến: Transaction Log Tailing (dùng CDC như Debezium đọc binlog/WAL) hoặc Polling Publisher (truy vấn SQL định kỳ). Relay đảm bảo cơ chế At-Least-Once delivery.

Act 04 — Case Study

KBM: Apply It

Outbox Pattern giải quyết bài toán data consistency trong mô hình Event-driven của KBM.

Gap Analysis — KBM Event Flows

Đánh giá rủi ro và chiến lược áp dụng Outbox
Nghiệp vụ (Flow) Rủi ro mất mát Mức độ Chiến lược Outbox áp dụng
Join Course Mất event gây mất dữ liệu điểm danh, sai lệch danh sách lớp ở các service khác. HIGH Dùng Transactional Outbox với CDC (Debezium). Relay chính xác lên Kafka topic course-events.

Implementation Roadmap

Các bước triển khai Outbox Pattern tại KBM
Phase 1 · Tuần 1

Thiết kế Schema Outbox & Event

Khởi tạo bảng outbox_events trong PostgreSQL. Chuẩn hóa Event Schema dùng JSON Schema hoặc Apache Avro để đảm bảo backward compatibility.

Dự kiến: 1 dev × 4 ngày
Phase 2 · Tuần 2

Tích hợp Outbox write vào Local Transaction

Sử dụng @Transactional trong Spring Data JPA để insert record vào outbox_events song song với Entity. Cấu hình Unit test đảm bảo rollback khi gặp lỗi.

✓ Đảm bảo Atomicity
Phase 3 · Tuần 3

Deploy Debezium & Kafka Connect (CDC)

Triển khai Debezium Postgres Connector. Lắng nghe WAL (Write-Ahead Log) của bảng outbox và streaming event trực tiếp sang Kafka, không làm tăng latency của luồng chính.

Dự kiến: 2 devs × 1 tuần
Phase 4 · Tuần 4

Xây dựng Idempotent Consumer

Do Outbox mang tính chất At-Least-Once, Consumer có thể nhận duplicate message. Bắt buộc triển khai Idempotency Key check (dùng Redis hoặc DB Unique Constraint) ở các Downstream Services.

✓ Xử lý Idempotency

Khi nào dùng — Khi nào không

[OK]
Nên dùng Transactional Outbox khi
  • Cần đảm bảo absolute consistency giữa Local DB update và message publish.
  • Hệ thống giao tiếp Event-driven bất đồng bộ giữa các microservices.
  • Sử dụng trong Saga Pattern (choreography) để trigger các step tiếp theo.
  • Tối ưu latency cho write request (không block chờ Broker ACK).
[Error]
Không cần dùng khi
  • Các message không quan trọng, chấp nhận mất mát (Tracking log, metrics).
  • Database không hỗ trợ Local ACID transaction đa bảng (ví dụ: một số NoSQL).
  • Nghiệp vụ thuần synchronous API, ưu tiên fail-fast.
  • Hệ thống Consumer không có khả năng handle Idempotency.
