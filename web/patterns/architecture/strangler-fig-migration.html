Act 01

The Problem

Hệ thống scale up, team mở rộng, thời gian deploy tăng dần. Yêu cầu chuyển đổi sang microservices trở nên cấp thiết, nhưng việc "rewrite toàn bộ" tiềm ẩn rủi ro quá lớn.

Coupling

Tight Coupling

Các module (Auth, Course, Judge) share chung database. Một schema migration có thể gây table lock toàn hệ thống, dẫn đến rủi ro sập production.

Bottleneck

All-or-Nothing Deploy

Thời gian release phụ thuộc chéo giữa các team. Mỗi lần deploy là một quá trình kéo dài và rủi ro.

Scale

Inability to Scale Independently

Tăng tải cục bộ đòi hỏi scale toàn bộ monolith. Gây lãng phí tài nguyên và ảnh hưởng performance các module khác.

Risk

The Big Bang Rewrite Trap

Dự án "rewrite toàn bộ" kéo dài, thiếu feature parity, và thất bại, để lại monolith với technical debt lớn hơn.

2
Act 02

The Pattern

Tách dần chức năng khỏi monolith theo từng sprint, duy trì monolith phục vụ traffic hiện tại. Sử dụng API Gateway làm seam để route traffic sang service mới hoặc fallback về monolith. Quá trình thay thế diễn ra liên tục cho đến khi loại bỏ hoàn toàn monolith.

— Strangler Fig Application · Martin Fowler (2004) · [W2]

Lấy cảm hứng từ loại cây strangler fig — bám vào cây chủ và dần thay thế cho đến khi cây chủ biến mất hoàn toàn.

Thành phần 01

API Gateway (The Seam)

Entry point duy nhất điều hướng traffic. Transparent với client về việc backend là monolith hay microservice.

Thành phần 02

New Service

Phát triển song song, deploy độc lập, database riêng biệt. Tiếp nhận traffic sau khi verify qua Canary hoặc Parallel Run.

Thành phần 03

Monolith (Legacy)

Tiếp tục xử lý traffic cho các module chưa tách. Kích thước giảm dần, tiến tới retire hoàn toàn hoặc làm fallback.

Act 04 — Case Study

KBM: Apply It

KBM LMS đang phục vụ production traffic hàng ngày. Không thể thực hiện Big Bang rewrite. Dưới đây là migration roadmap áp dụng Strangler Fig theo mức độ ưu tiên.

Gap Analysis

Các module cần extract, sắp xếp theo risk level

ModuleCurrent IssuesRiskStrangler Strategy
Auth Sử dụng shared secret HS256, stateful session, thiếu cơ chế token revocation HIGH Route-based: /auth/* → Keycloak
Core ↔ Assignment Shared database gây schema lock incidents khi high traffic HIGH Schema sep → view abstraction → separate DB + Outbox
Judge (SQL) CPU bottleneck, không có khả năng scale độc lập MED Event-based: Kafka topic → Judge workers độc lập
Notification Tight coupling Email/WebSocket với Core Service LOW Async: Core publish events → Notification subscriber

Migration Timeline

Ưu tiên Quick Wins, mitigate High-Risk tasks sau

Tuần 1–2 · Phase 0

Triển khai API Gateway

Deploy Spring Cloud Gateway phía trước monolith. Ensure 100% request pass-through với latency < 5ms. Fully reversible.

Effort: 1 dev × 2 ngày
Tuần 3–4 · Phase 1

Extract Auth → Keycloak (Canary Deploy)

Deploy Keycloak, migrate credentials. Canary route /auth/* sang Keycloak 10%. Monitor telemetry 48h, switch 100%, tiến hành delete Auth code khỏi monolith.

✓ Independent deploy achieved
Tháng 2–3 · Phase 2

Database Schema Separation

Tách shared PostgreSQL. Implement Outbox Pattern cho distributed events. Sử dụng database views làm abstraction layer bảo đảm zero downtime.

Effort: 2 devs × 3 tuần
Tháng 4–6 · Phase 3

Extract Judge Service (Event-driven)

Judge workers consume Kafka topic. Cho phép scale độc lập CPU/Memory khi tải cao. Parallel run 2 tuần trước khi cutover.

✓ Independent scaling achieved

Khi nào dùng — Khi nào không

Yes
Phù hợp khi
  • Hệ thống chạy production yêu cầu zero downtime
  • Yêu cầu gradual migration, hỗ trợ rollback dễ dàng
  • Domain có bounded context rõ ràng
  • Team đủ resource cho parallel development
  • Architecture hỗ trợ tích hợp API Gateway
No
Không phù hợp khi
  • Hệ thống nhỏ, chi phí vận hành (overhead) cao
  • Monolith có kiến trúc modular tốt
  • Thiếu observability, khó monitor migration process
  • Database coupling sâu (stored procedures, triggers)
  • Team thiếu kinh nghiệm distributed systems
