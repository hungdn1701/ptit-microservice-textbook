Act 01

The Problem

Khi giao tiếp đồng bộ qua REST API, hệ thống bị phụ thuộc (tight coupling) vào tính sẵn sàng của dịch vụ đích. Nếu dịch vụ đích chậm hoặc crash, luồng xử lý của caller sẽ đứt gãy.

[Waiting]

Thread Blocking ở caller

Khi gọi REST đồng bộ từ kbm-core sang kbm-judge-sql, do biên dịch tốn 2-5s, thread của caller bị block. Dưới tải cao, thread pool cạn kiệt, gây treo hệ thống.

[Error]

Mất message (Message Loss)

Nếu kbm-judge-sql gặp sự cố crash do quá tải CPU, mọi request đến lúc đó sẽ failed (lỗi 500). Dữ liệu nộp bài bị mất vĩnh viễn, không thể khôi phục.

Act 02

The Pattern

Chuyển đổi sang giao tiếp bất đồng bộ: Producer đẩy message vào Topic trên Message Broker. Broker lưu message bền vững trong các log file (chia thành các Partitions). Các Consumers kết hợp thành Consumer Group để chia sẻ tải đọc partitions và xử lý song song (pull-based).

— Message Broker Pattern · Enterprise Integration Patterns

Cơ chế Offset đánh dấu vị trí message đã consume. Nếu consumer crash và khởi động lại, nó sẽ resume từ Offset đã commit gần nhất, đảm bảo at-least-once delivery và chống mất data.

Thành phần 01

Topic & Partitioning

Message được lưu trong Topic. Để scale-out, Topic được chia thành nhiều Partitions phân tán trên các Broker, giúp tăng throughput đồng thời.

Thành phần 02

Consumer Group

Nhóm các consumer instances cùng consume một Topic. Mỗi Partition chỉ assign cho tối đa 1 Consumer trong group, đảm bảo message ordering trong phạm vi partition.

Thành phần 03

Offset Commitment

Chỉ số vị trí message trong partition. Sau khi xử lý, consumer Commit Offset về Kafka, xác nhận đã hoàn thành xử lý, giúp an toàn phục hồi khi có sự cố.

Act 04 — Case Study

KBM: Apply It

KBM sử dụng Apache Kafka làm event streaming pipeline, giúp bảo vệ master node trước traffic spike khi nộp bài.

Gap Analysis & Message Broker Options

So sánh cấu trúc Queue và Log-based
Tiêu chí RabbitMQ (Classic Queue) Apache Kafka (Log-Based) Lý do chọn Kafka cho KBM
Khả năng Replay (Chấm lại) Không hỗ trợ (message bị xóa sau khi ack). Có (Lưu trữ bằng append-only log trên disk). Hỗ trợ rewind offset để re-process (chấm lại) khi test case thay đổi.
Message Ordering Khó đảm bảo khi có nhiều concurrent consumers. Đảm bảo strict ordering theo Partition. Dùng studentId làm routing key để đảm bảo các bài của một user xử lý tuần tự.

Lộ trình triển khai hạ tầng Kafka

Các bước tích hợp an toàn hệ thống hàng đợi
Phase 1 · Tuần 1

Provision Kafka Cluster & Partitions

Cài đặt Kafka KRaft mode. Tạo topic submissions với 3 partitions để map 1-1 với 3 Judge instances nhằm tối ưu load balancing.

Dự kiến: 1 dev × 3 ngày
Phase 2 · Tuần 2

Tích hợp Spring Kafka Producer vào kbm-core

Dùng KafkaTemplate. Gắn Message Key là studentId để đảm bảo request từ cùng user được route vào một partition (strict ordering).

✓ Async non-blocking API
Phase 3 · Tuần 3

Cấu hình Consumer Group ở kbm-judge-sql

Dùng @KafkaListener(groupId="judge-group"). Khai báo concurrency để auto-assign partitions và xử lý message song song.

Dự kiến: 2 devs × 1 tuần
Phase 4 · Tuần 4

Triển khai Dead Letter Queue (DLQ)

Các message lỗi (gây crash hoặc exceed retry limit) sẽ chuyển sang submissions-dlq để tránh poison pill block toàn bộ luồng xử lý.

✓ Fault tolerance & Resilience

Khi nào dùng — Khi nào không

[OK]
Nên dùng Apache Kafka khi
  • Cần async communication để decouple producer và consumer.
  • High write throughput (Event streaming, Logs, Metrics).
  • Cần replayability (Event sourcing, data processing pipeline).
  • Cần strict ordering dựa trên message key.
[Error]
Không nên dùng khi
  • Kiến trúc monolith đơn giản, tải thấp (Over-engineering).
  • Yêu cầu synchronous request-response (RPC/REST phù hợp hơn).
  • Hạ tầng hạn chế RAM/Disk (Kafka tốn nhiều resources).
  • Consumer chưa handle được idempotency.
