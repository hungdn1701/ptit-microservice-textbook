Act 01

The Problem

Microservices cần vừa ghi vào database vừa gửi event lên Kafka. Nếu làm 2 thao tác riêng biệt (dual-write), sẽ xảy ra tình huống không nhất quán: DB thành công nhưng Kafka thất bại, hoặc ngược lại.

⚠️ Dual-Write Problem: Không thể đảm bảo atomic giữa 2 hệ thống khác nhau (DB + Message Broker) mà không dùng distributed transaction (2PC) — vốn chậm và phức tạp. Outbox Pattern giải quyết bằng cách biến thành 1 write duy nhất vào DB.
Lost Event

Mất sự kiện (Lost Events)

DB ghi thành công, nhưng Kafka publish thất bại. Consumer không nhận được event. Dữ liệu giữa các services bị lệch mà không ai biết.

Ghost Event

Sự kiện ma (Ghost Events)

Kafka publish thành công, nhưng DB transaction rollback. Consumer xử lý event cho một thay đổi chưa bao giờ tồn tại trong DB.

Act 02

The Pattern

Outbox Pattern: Thay vì publish trực tiếp lên Kafka, ứng dụng ghi event vào bảng outbox trong cùng 1 DB transaction với business data. Sau đó, Debezium (CDC connector) đọc transaction log của DB và tự động đẩy event lên Kafka.

— Transactional Outbox + CDC · Chris Richardson / Debezium.io
Thành phần 01

Outbox Table

Bảng outbox_events cùng DB với business data. Mỗi row = 1 event: {id, aggregate_type, aggregate_id, event_type, payload, created_at}. INSERT cùng transaction.

Thành phần 02

Debezium CDC Connector

Kafka Connect connector đọc PostgreSQL WAL (Write-Ahead Log). Bắt mọi INSERT vào bảng outbox → chuyển thành Kafka message. Zero-code, không cần sửa ứng dụng.

Thành phần 03

Outbox Event Router

Debezium SMT (Single Message Transform) route event tới đúng Kafka topic dựa trên aggregate_type. Bảng outbox_events được dọn dẹp riêng bằng scheduled job hoặc retention policy.

Act 04 — Case Study

KBM: Apply It

KBM sử dụng Outbox Pattern + Debezium CDC để đảm bảo mọi thay đổi nghiệp vụ đều được publish lên Kafka mà không cần sửa code ứng dụng.

Outbox Events trong hệ thống KBM

Mỗi aggregate type tương ứng 1 Kafka topic
Aggregate Type Event Types Kafka Topic Consumers
Enrollment ENROLLED, DROPPED outbox.event.enrollment Notification Svc, Analytics Svc
Payment PAID, REFUNDED outbox.event.payment Enrollment Svc (confirm), Email Svc

Lộ trình triển khai CDC + Outbox

Từ polling đến streaming
Phase 1

Outbox Table + Polling Publisher

Tạo bảng outbox_events. Dùng scheduled job poll mỗi 500ms để đọc và publish pending events. Đơn giản nhưng có latency.

Phase 2

Debezium CDC Connector

Thay polling bằng Debezium Kafka Connect. Đọc WAL trực tiếp → near real-time. Cấu hình outbox.event.router SMT để route theo aggregate_type.

Phase 3

Idempotent Consumers

Consumer side lưu event_id vào bảng processed_events (UNIQUE constraint). Đảm bảo at-least-once delivery + idempotent processing.

Phase 4

Monitoring & Alerting

Dashboard Debezium metrics: replication lag, connector status, WAL disk usage. Alert nếu lag > 5 phút hoặc connector down.

Khi nào dùng — Khi nào không

✓
Nên dùng Outbox + CDC khi
  • Cần đảm bảo exactly-once giữa DB write và event publish.
  • Muốn zero-code approach — không cần sửa ứng dụng hiện tại.
  • Data migration: stream changes từ monolith DB sang microservice.
  • Audit trail: mọi thay đổi dữ liệu đều được capture.
✗
Không nên khi
  • Hệ thống đơn giản — polling publisher đủ tốt (< 100 events/s).
  • DB không hỗ trợ logical replication (một số managed DB).
  • Team chưa quen Kafka Connect — ops complexity cao.
  • Event không cần guaranteed delivery (analytics, logging).
